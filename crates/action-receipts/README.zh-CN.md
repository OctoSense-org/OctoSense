# 可恢复的宿主动作

[English](README.md) | 简体中文

这是一个可选的原生宿主执行记录库，解决服务端已经接收动作、本机却丢失回执后的恢复问题。[补位](https://github.com/WeiR-h/buwei)已将同一实现用于活动邀请、本人报名与回复、社群发布和文章发布。

该库使用独立工作区，不加入默认 Shell 构建，不修改现有宿主服务、权限或界面。其他服务接入时需单独审核适配器。

## 执行约定

1. 可信宿主将 `Authority` 绑定到 SDK 核实的当前账号，在本人授权后签发不可序列化的 `Grant`。
2. `prepare` 保存确切动作、身份、业务版本、内容摘要和确认期限。
3. `confirm` 核对当前授权与适配器的业务版本。
4. `execute` 先持久化认领操作，再执行；适配器用原操作编号作为服务端交易编号。
5. 回执必须同时匹配操作编号、账号、对象和完整内容摘要，结果不明时保留待核实状态。
6. `reconcile` 只查询原操作。相同账号重新授权后可以核实旧结果，不重新发送。

账号变化、撤销授权使旧确认失效。候补顺序和容量由业务层检查。SQLite 索引按应用、账号和状态查询，避免历史记录增多后全表扫描。

## 复现

需要 Rust 1.98.0 和用于编译 SQLite 的 C 工具：

```sh
cargo test --manifest-path crates/action-receipts/Cargo.toml --locked
cargo run --manifest-path crates/action-receipts/Cargo.toml --locked --example benchmark_recovery
```

基准在相同 50,008 条合成记录上，对比索引迁移前后的生产查询并核对结果一致。数据只反映本地数据库耗时，不发起网络或模型请求。

单元测试使用受控适配器。真实 SDK 行为由补位的独立双账号脚本另行验证；单元测试通过不代表另一个宿主已完成接入。宿主提供时钟；适配器必须在外部动作前重新检查当前身份和权限，并核验服务端证据，不能把套接字写入成功当成回执。

Apache-2.0。源码不含密钥、登录会话和原始用户记录。

另一个 `benchmark_owned_history` 示例将 50,008 条记录全部归于同一账号，其中 50,005 条为已核验历史结果、3 条待核实，用于区分恢复状态索引与跨账号筛选的收益。使用相同命令并把示例名改为 `benchmark_owned_history` 即可运行。
