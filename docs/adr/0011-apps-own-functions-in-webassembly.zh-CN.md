# ADR 0011：应用自带的 WebAssembly 函数

[English](0011-apps-own-functions-in-webassembly.md) | 简体中文

状态：已接受（2026-10-08），有限支持。外壳的 `wasm-functions` 特性（原名 `wasm-lab`）在每个
标准桌面版和 Home 构建中开启，服务在 macOS、Linux 和 Android 上运行。Windows（尚未检查）、
iOS（应用不允许生成代码）和 OpenHarmony（策略未知）不包含这个运行时。契约部分在 App Hub #140
（app-contract 1.7.0）。已在 macOS 的隐藏桌面外壳中、Linux 的无头桌面中，以及 Android 手机上
验证：单独打包的 Home 中的 Redmi Note 12，以及手机验收中的 OnePlus 6。iOS 和 OpenHarmony 尚未
尝试。`main` 上的实现方式、限制和检查见 [OctoSense 中的 WebAssembly](../wasm.zh-CN.md)。

## 背景

脚本应用使用 Splash：受隔离、解释执行，能力以运行时提供的为限。应用里有些逻辑更适合用
Rust 写：解析器、排序或排程算法、差异比较、格式转换，或者现成的、正好能完成任务的 crate。
目前为应用运行 Rust 只有两种方式：原生应用（链接进外壳，完全受信任，不适合第三方）或宿主
服务（外壳自己的代码，由我们编写）。Splash 的计算内核适合数值计算，不适合通用 Rust。

我们希望开发者能把自己的 Rust 函数放进应用包里，由外壳只为这个应用运行，而且不引入新的
信任：函数能接触的不超过应用本来能接触的，除了自己的输入和输出，什么都接触不到。

## 决定

1. **模块。** 应用包可以在 `fns/*.wasm` 中携带核心 WebAssembly 模块（最多 8 个）。
   模块导出 `memory`、`octo_alloc(len) -> ptr`、`octo_free(ptr, len)` 和它的函数；
   每个函数的签名是 `(ptr, len) -> i64`，返回 `(out_ptr << 32) | out_len`，输出的第一个
   字节是状态（0 成功，1 出错）。唯一允许的导入是 `octo.log(ptr, len)`。一个小的客体 crate
   （`apps/wasmlab/guest/octosense-guest`）为 `fn(&[u8]) -> Result<Vec<u8>, String>` 和
   serde 类型生成这一切。这一版不用组件模型，也不用 WASI。
2. **运行时。** `crates/wasm-host` 在 Wasmtime 49 中运行模块，模块加载时由 Cranelift
   编译。编译结果缓存在宿主目录中，以模块摘要和引擎兼容性哈希为键。每次调用都有截止时间
   （2 秒，按实际经过的时间做 epoch 中断）；内存（256 MiB）、表元素（16,384 个）、wasm 栈（512 KiB）、模块
   （8 MiB）以及输入输出（16 MiB）都有上限。陷阱或超时只让这次调用出错，绝不结束进程，
   并作废这个实例：下次调用会得到新实例，因为 Rust 客体的栈指针和分配器可能只更新了一半。
3. **`wasm` 宿主服务**（外壳特性 `wasm-functions`，原名 `wasm-lab`）。`wasm.<function>` 调用发起请求的应用自己的
   函数；`wasm.functions` 列出这些函数、加载情况和运行统计。字符串参数按文本传入，
   其他参数按 JSON 传入；JSON 输出作为数据返回，其他输出返回 `{"text": …}`。
   模块只来自调用应用自己通过准入、经过摘要检查的应用包，而不是请求参数指定的文件。
   每次调用都使用全新实例，包括上次成功或返回客体错误的情况；内存、全局变量、表和
   日志不能把某次调用的输入带到下一次。只复用编译后的 Program。底层运行时仍为基准
   测试提供可复用的 `Instance` API，但应用服务不复用实例。

   服务最多允许四个活动工作线程，每个应用最多排队四个请求；每个请求序列化后的输入
   不超过 1 MiB，所有排队及正在执行的输入合计不超过 16 MiB。队列已满时立即返回错误，
   不阻塞界面线程。工作线程空闲五秒后释放 Program 并退出。每个请求从排队到加载有
   十秒总预算；客体启动函数与导出函数共享最多两秒的执行预算，每次 epoch 检查取消。
   编译本身不能被中断，但过期或已取消的请求不会在编译后继续执行。
   入队只复制宿主持有的准入身份引用，不在界面线程读取应用包、验签或计算摘要。
   第一次冷启动请求在工作线程首次验证准入时绑定身份；`ServiceCall` 并不携带发起
   请求的界面已加载版本的令牌。后续排队请求保留该已验证版本。工作线程在执行前和
   交付结果前重新检查准入；应用包、权限发生变化或签名目录撤回应用时，丢弃结果和
   缓存的 Program 引用，并使旧身份失效。此后的新请求可以加载新代码；已经排队的
   旧请求仍会被拒绝。正在关闭的工作线程在释放队列和编译模块之前继续占用全局名额。
   磁盘缓存只包含编译代码，不包含客体状态。
4. **`wasm` 能力**加入 App Hub 封闭的能力列表。商店的说明是：“在此设备上的沙盒中运行它
   自带的函数；这些函数接触不到文件、网络或其他应用。”
5. **Agent 工具。** 工具可以写 `host_method: "wasm.<function>"`：应用的 Agent（以及在
   共享时的其他调用者）运行这个应用自己的函数。它需要 `wasm` 能力；与共享宿主方法不同，它
   没有风险下限，也不要求 `private_data`：函数只能看到传给它的参数。

## 实测过的替代方案

M5 Max 上的 CoreMark（越高越快；原生 Rust 约 45,000）：

| 运行时 | CoreMark | 说明 |
| --- | --- | --- |
| Wasmtime + Cranelift（选定） | 44,534 | 二进制增加 7.4 MiB；模块加载时编译 |
| WasmEdge AOT | 30,432 | 库 153 MiB；编译 0.2–0.36 秒 |
| stitch（解释器） | 2,942 | 与 Makepad 契合，无 JIT；需要一个宿主调用修复（makepad #106） |
| Pulley（Wasmtime 的解释器） | 2,587 | 无 JIT：iOS 的选项 |
| WasmEdge 解释器 | 374 | |

- **原生动态库**没有隔离；Theseus OS 的模型（受信任的编译器、单一地址空间）不适用于手机
  操作系统。
- **上游 Makepad 的 JIT** 编译的是 Splash，不是 Rust。
- **Splash 计算内核**仍然是数值内核的答案。

## 测量（Wasm Lab，`apps/wasmlab`）

以下是服务改为每次调用使用全新实例之前的原始运行时测量，不代表本次加固后的
端到端服务性能。

只有轻量算法：Markdown 转 HTML（pulldown-cmark）、在忙碌时段之间找空闲时段、模糊排序
（strsim）、按行差异比较（similar）。

200 次调用的中位数，release 构建，桌面运行三次、手机运行三次
（`cargo run --release -p octosense-wasm-host --example measure`；手机上是同一个示例，
交叉编译后通过 adb 运行）：

| | 桌面（M5 Max） | 手机（Redmi Note 12，骁龙 685） |
| --- | --- | --- |
| 模块 | 433 KiB | 433 KiB |
| 编译（首次加载） | 27–33 毫秒 | 378–421 毫秒 |
| 从缓存加载 | 新进程中 1.0–1.4 毫秒；刚写入后 4.8–6.4 毫秒 | 5.0–7.0 毫秒 |
| 实例化 | 0.07 毫秒 | 0.19–0.27 毫秒 |
| md_to_html，32 KiB | 405–412 微秒（原生的 2.1–2.2 倍） | 2,325–2,328 微秒（1.7 倍） |
| find_slots，30 个忙碌时段 | 6.7 微秒（1.7 倍） | 40 微秒（1.5 倍） |
| fuzzy_rank，500 项 | 138–146 微秒（1.6–1.7 倍） | 841–845 微秒（1.4 倍） |
| text_diff，1000 行 | 231–254 微秒（1.6–1.7 倍） | 1,434 微秒（1.9 倍） |
| 最小调用（双向 JSON） | 0.3 微秒 | 2.5–2.6 微秒 |

用 wasm SIMD（`+simd128`）构建客体没有缩小 Markdown 的差距（2.2–2.3 倍）：差距来自
Cranelift 与 LLVM 的代码生成，而不是向量化。Wasmtime 和 Cranelift 给 Android 库增加约
7.5 MiB 代码（按符号大小；桌面上测得 7.4 MiB）。

在外壳中，脚本用 `host.request` 调用自己的函数并收到结果，桌面上约 2 毫秒，手机上
1.8–2 毫秒，几乎全部花在 UI 事件循环上；函数本身在桌面上用 18–72 微秒，在手机上用
47–190 微秒。在手机的 Home 中，模块首次启动时编译用了 670 毫秒（应用当时还在启动），之后
从缓存加载用 7.4–11 毫秒。四种失控模式（死循环、无限分配、panic、无限递归）分别在
2,000 毫秒、140 毫秒、2.2 毫秒和 3 毫秒后以错误结束，Home 一直在运行。

两个平台发现：

- **Android 上的陷阱需要 libc 0.2.190。** 使用 libc 0.2.189 时，Wasmtime 通过信号捕获的
  每一种陷阱（panic 的 `unreachable`、越界读取、栈溢出）都会让 Home 退出，普通的命令行
  程序也一样。Wasmtime 的信号处理函数确实运行了，但它通过 libc 的 `ucontext_t` 读取出错
  位置的 pc，而 aarch64 Android 的这个结构缺少内核在信号掩码后面加的填充，所以没有一个
  陷阱被认出是 wasm。0.2.190 修正了这个布局；`crates/wasm-host` 现在要求这个版本。显式陷阱
  （`signals_based_traps(false)`）也能工作，但每次调用慢 19–38%，编译时间翻倍。
- **桌面上的扫描程序会让缓存比编译还慢。** 在受管理的 Mac 上，Microsoft Defender 会把新写入
  的缓存文件的第一次打开挡住约一秒；外壳的新构建第一次打开它时又会被挡一次（1,086 毫秒；
  下次启动 2.3 毫秒）。写入方会在后台把文件读一遍，但只能覆盖第一种情况。那里编译只要
  30–60 毫秒，所以桌面可以不用缓存，或让两者竞速；在手机上，缓存能省下约 0.4 秒。

## 影响

- 对这些工作负载，第三方 Rust 在 OctoSense 应用中的运行时间是原生的 1.4–2.2 倍，不引入
  新的信任，默认构建不变。
  *2026-10-08：以有限支持的方式接受。macOS、Linux 和 Android 上的标准构建现在包含这个服务及其
  运行时，约 7.5 MiB 代码。*
- Android APK 增加 3.5 MiB（从 209.1 MB 到 212.8 MB，含 Wasm Lab 自己的应用包）；运行时
  约为 7.5 MiB 代码。
- 在中端手机上，每个模块编译约 0.4 秒（Home 启动期间 0.67 秒）。有了缓存，之后的加载只要
  5–11 毫秒；在安装时编译（商店应用）或在构建时编译（系统应用）可以省掉第一次。
- 在 App Hub #140 的商店检查下，商店应用包可以携带 `fns/*.wasm`（核心模块，最多 8 个，
  只能配合 `wasm` 能力）。到目前为止，只有系统应用在设备上运行过函数。
- iOS 不允许应用使用 JIT，也不允许下载原生代码：那里只能用 Pulley（比 Cranelift 慢约
  17 倍）。随系统发布的应用，其函数可以在构建应用时转成原生代码；商店应用不行。
  OpenHarmony 的 JIT 策略未知（**未验证**）。
- 客体内存不再跨调用或在八个模块间保留：每个工作线程最多有一个活动实例，最多
  四个工作线程。持续准入的请求仍可占满这些线程；应用间 CPU 公平调度和磁盘编译缓存
  的有界淘汰策略仍待实现。编译后的 Program 也会占用线性内存上限以外的宿主内存。
- 运行时和外壳服务回归测试覆盖真实 Wasm 状态残留、表扩容、取消、输入/队列上限、
  版本/权限变化及签名目录撤回。本次加固尚未在手机上重新验证。
  *2026-10-08：此后[手机验收](../../tools/fixtures/wasm-phone-lab/README.zh-CN.md)已在一部 OnePlus 6 上
  覆盖这项加固（22 项检查全部通过）。*

## 未决问题

- 用带类型的接口（组件模型和 WIT）代替 JSON 输入输出。
- `octo.log` 之外的任何宿主导入（时钟、随机数）都应是新的能力，而不是默认提供。
- epoch 截止时间开销小但不确定；fuel 是确定的，但有代价。
