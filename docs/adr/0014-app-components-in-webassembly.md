## Context

ADR 0011 lets an app ship Rust functions as core WebAssembly modules. They are
fast, since Cranelift compiles them, but they are sealed:
- a module's only import is `octo.log`, so it reaches no clock, randomness, file
  or network;
- every call gets a fresh instance, so nothing persists between calls;
- input and output are bytes or JSON through a hand-written ABI;
- a developer copies a guest crate out of OctoSense to write one.

Most crates on crates.io either need some of what is missing (a clock, random
numbers, files) or keep state between calls, such as a parsed document, a cache
or a model. So few crates can be used as they are.

Browsers solved the same problem: WebAssembly there imports platform APIs
through JavaScript, keeps its state, and gets typed glue generated by
`wasm-bindgen`. Outside the browser, the standard answer is the WebAssembly
**component model**: typed interfaces (WIT) and **WASI 0.2** system
interfaces. Rust has built components directly since 1.82
(`--target wasm32-wasip2`, Tier 2), and the Wasmtime we already ship implements
both (`wasmtime-wasi` 49).

We want a developer to take an ordinary crate, build it with one command, and
call its functions from their app's script, with no glue and no new trust. A
component reaches only what its app may already reach.

## Decision

1. **Components beside modules.** A bundle's `fns/*.wasm` may be a component
   or a core module. The runtime tells them apart by the preamble
   (`component::is_component`). Modules keep ADR 0011's contract. A component
   is built with plain `cargo build --target wasm32-wasip2`.
2. **Typed functions, called with JSON.** Every function a component exports is
   callable from the app's script with no glue:
   - A world's own functions are called as `wasm.<function>`, and functions in
     an exported interface as `wasm.<interface>.<function>`.
   - `wasm.functions` lists each one with its WIT signature.
   - Arguments are an object keyed by parameter name, an array in parameter
     order, or, for one parameter, the value itself.
   - WIT types map to JSON:
     - a record is an object, and a tuple is an array;
     - a variant is `"case"` or `{"case": value}`, an enum is its name, and
       flags are a list of names;
     - an option is `null` or the value, a `char` is one character, numbers are
       range-checked, and `list<u8>` is base64 text (an array of numbers is also
       accepted).
   - A function's `result<T, E>` return is its value, or the call's error with
     `E`.
   - Functions that take or return a resource are not callable from scripts.
     They're listed as skipped, with the reason.
3. **Instances keep their state.** One instance per component lives for as long
   as the app's worker, so a component can hold a document, a cache or a model.
   A worker holding one waits a minute for the next call, not five seconds. A
   trap or a deadline spends the instance; the next call gets a fresh one. An
   update, a grant change or a withdrawal discards it, as for modules.
4. **WASI scoped to the app's resources and account.**
   - **Always:** `wasi:clocks`, `wasi:random`, `wasi:io` and `wasi:cli`.
     stdout and stderr become the app's log lines (bounded). The environment,
     arguments and stdin are empty.
   - **`wasi:filesystem`:** the app's available storage area, with its active
     account for an account-scoped app, decided per call by the rules an
     engine's folder follows. Its storage folder is preopened as `/`,
     read-write, and nothing else of the host's filesystem is visible. No
     available area means no preopen. `storage` is a disclosure declaration.
   - **The storage quota, per write.** A call may add what is left of the
     app's quota when it starts. The runtime replaces the WASI calls that
     grow a file (`write`, `set-size`, and the streams `write-via-stream` and
     `append-via-stream` hand out) with ones that charge the growth, and the
     calls that free bytes (`open-at` truncating, `unlink-file-at`) with ones
     that give them back. Past the budget a write fails inside the component,
     and the call's error says why. A check after each call instead was
     rejected: a call could write gigabytes before it, and it costs two walks
     of the folder a call.
   - **`wasi:http` outgoing, phase 3:** to any host. The app declares `net`,
     so that its install sheet says it uses the network, but neither that
     nor `network.hosts` is enforced while it runs: the ruling of
     8 October 2026 removed the per-app runtime gates, and the OS and the
     host's API surface are the boundary. Holding a component to its app's
     `network.hosts`, and then to public HTTPS hosts, was rejected under that
     ruling. A request waits outside the guest, where the epoch check cannot
     end it, so its timeouts are clamped to the call's deadline, which is
     10 s for a component that imports `wasi:http`.
   - **`octosense:host`, phase 3:** `request(service, args)` reaches the host
     services as the app's script's `host.request` does, dispatched on the UI
     thread and, since makepad#118 (OctoSense #450), not checked against the
     families the manifest declares. Each service retains its actual
     app/account, consent, review and resource checks. Calls gain no sheet or
     prompt (only methods a background surface may call), and never `wasm.*`.
   - **Never:** `wasi:sockets`, and any import outside these packages. A
     component that asks for one is refused when it loads
     (`LoadError::Import`) and by App Hub's gate.
5. **No WIT to write.**
   - **Guest SDK, phase 2:** a guest crate, `octosense-component`, with an
     `#[octosense_component::export]` attribute that derives the WIT world from
     ordinary Rust signatures. These include numbers, `String`, `Vec<T>`,
     `Vec<u8>`, `Option`, `Result<T, String>`, and structs and enums marked for
     export.
   - **Tooling, phase 2:** App Flow's `octo` gains:
     - `octo wasm new`, which writes a crate template;
     - `octo wasm build`, which builds it, checks its imports against the
       manifest and writes `fns/`;
     - `octo wasm doctor`, which names dependencies that cannot build for
       `wasm32-wasip2` (C libraries such as `openssl-sys` or `libsqlite3-sys`,
       threads, multi-threaded runtimes) and suggests replacements.
   - **Distribution:** the SDK goes on crates.io (with the maintainer's
     approval), and until then on a git dependency.
6. **Admission sees what a component reaches.** App Hub's gate reads each
   component's imports:
   - it refuses any outside the allowed set;
   - it records filesystem, HTTP and host imports for disclosure; it does not
     require a matching capability declaration as execution permission;
   - it tells reviewers what the component reaches, for example "files in its
     app folder; the network".
   Components need a new app contract version.

## Phases

| Phase | Scope |
| --- | --- |
| 1. Runtime spike (done here) | `crates/wasm-host::component`: load, check imports, list exports with WIT signatures, long-lived instances, JSON calls, the WASI subset above with the storage preopen, the deadline, the memory cap and logs. Tests run an unmodified crate (`pulldown-cmark`) built with plain cargo, and refuse a component that imports `wasi:sockets`. |
| 2. Usable by developers | The shell's `wasm` service: loading components from `fns/`, `wasm.<function>` calls, per-app instances, the app's available storage area, and storage quota accounting for component writes. A larger input limit for components. The guest SDK and its macro; `octo wasm new/build/doctor`; App Hub's gate check and contract version; docs and an example app. |
| 3. Reach and platforms | `wasi:http` outgoing to any host (declared with `net`, not enforced); an `octosense:host` import for host services under the same checks as `host.request`; compiling at install time, so a phone skips the first compile; Pulley (Wasmtime's interpreter) on OpenHarmony until its JIT policy is known; Windows runtime tests in CI. iOS remains outside the current plan. |
| 4. Shared components | Reviewed, versioned components in App Hub's catalog that apps depend on, like npm packages. The installer verifies them, and every app still gets its own instance, account and storage boundaries. |

## Alternatives considered

- **Stay with core modules and JSON (ADR 0011 as it is).** It stays safe, but
  few crates run as they are, and every type is hand-encoded.
- **A WASI 0.1 (preview 1) module ABI of our own.** It gives files and clocks,
  but no typed interfaces and none of the component tooling. Rust's
  `wasm32-wasip2` builds components by default.
- **Native Rust loaded into the shell** (dynamic libraries, or JIT-compiled Rust
  such as makepad's Relax). It's fast and complete, but the code runs in the
  shell's process with its privileges. Relax is tracked as an experiment, and
  third-party code needs isolation first.
- **A Wasm runtime of our own, or wasmi.** Wasmtime is already linked, compiles
  with Cranelift, and implements WASI 0.2 and the component model.

## Consequences

- **The shell's dependency graph grows.** It gains `wasmtime-wasi` 49.0.2
  (`p2` only) and the `component-model` feature. Both are linked wherever
  `wasm-host` already is (feature `wasm-functions`).
- **A component uses its app's resources and identity:** its available,
  quota-bounded private storage folder, outbound HTTP and available host services
  under the app/account and background-call checks. `storage`, `net` and
  `network.hosts` disclose use; omitting them does not deny execution. Clocks
  and randomness are new to Wasm but available to every script.
- **Persistent instances use memory for longer.** The per-app worker cap
  (`MAX_WORKERS`) and the memory cap bound it, and idle workers exit as today.
- **Spike sizes:** `notes` (with `pulldown-cmark` and `getrandom`) is 313 KiB;
  the sockets probe is 120 KiB.
- **A full disk looks like an I/O error.** wasi-libc reports any failed stream
  write as `EIO`, whatever error the host gives, so most refused writes reach
  the guest as an I/O error rather than `ENOSPC`. The runtime adds the reason
  to the call's error and to the app's log.

## Measurements

`cargo run --release -p octosense-wasm-host --example measure_component`, on
an Apple M5 Max with macOS 26.6.2 (9 October 2026). Each figure is a median
of 200 calls unless the row says otherwise. The module is Wasm Lab's
(ADR 0011), which runs the same `pulldown-cmark`.

| | Component | Module | Native |
| --- | --- | --- | --- |
| Compile with Cranelift, first load | 37.5 ms (313 KiB) | | |
| Load from the cache | 3.6 ms | | |
| Instantiate (with the storage folder) | 0.09 ms (0.10 ms) | | |
| Markdown to HTML, 32 KiB | 468 µs | 400 µs | 183 µs |
| Render and write 49 KiB to a new file | 678 µs | | 156 µs (the write) |
| Write a 12-byte file | 143 µs | | |
| Read 49 KiB back | 59 µs | | |
| 1 MiB of `list<u8>`, there and back as base64 | 18.4 ms | | |
| The smallest call | 0.2 µs | 0.3 µs | |

In Pulley (`OCTOSENSE_WASM_PULLEY=1`, `--features pulley`, same machine), the
Markdown function takes 15.1 ms as a component and 14.1 ms as a module: about
32 times Cranelift's code. The smallest component call is 0.4 µs. OpenHarmony
runs this until its code-generation policy is known.

The quota needs what the folder holds when a call starts: one walk of it, as
for an engine's call. That took 0.12 ms for 10 files, 2.0 ms for 1,000 and
23.8 ms for 10,000 (a median of 50). Rewriting one file over and over is
slow on APFS, natively too (a median of about 6 ms a rewrite), so the
example writes a new file each time.

## Open questions

Settled in phase 3: a component never calls a host service that opens a
sheet or asks the person; such a call belongs to the script.

- Async functions (WASI 0.3) and streaming bodies: after phase 3.
- iOS is outside the current plan. Any later proposal needs a separate Home
  build and device acceptance; Pulley tests do not establish iOS support.
