# ADR 0014: An app's Rust crates as WebAssembly components

English | [简体中文](0014-app-components-in-webassembly.zh-CN.md)

Status: Proposed (9 Oct 2026). Phase 1, the runtime spike, is in
`crates/wasm-host` (`src/component.rs`, `tests/component.rs`). Phases 2–4 below
are the plan. It extends [ADR 0011](0011-apps-own-functions-in-webassembly.md):
core modules keep working as they do. How WebAssembly runs on `main`:
[WebAssembly in OctoSense](../wasm.md).

## Context

ADR 0011 lets an app ship Rust functions as core WebAssembly modules. They are
fast, since Cranelift compiles them, but they are sealed:
- a module's only import is `octo.log`, so it reaches no clock, randomness, file
  or network;
- every call gets a fresh instance, so nothing persists between calls;
- input and output are bytes or JSON through a hand-written ABI;
- a developer copies a guest crate out of OctoSense to write one.

Most crates on crates.io either need some of what is missing (a clock, random
numbers, files) or keep state between calls, such as a parsed document, a cache
or a model. So few crates can be used as they are.

Browsers solved the same problem: WebAssembly there imports platform APIs
through JavaScript, keeps its state, and gets typed glue generated by
`wasm-bindgen`. Outside the browser, the standard answer is the WebAssembly
**component model**: typed interfaces (WIT) and **WASI 0.2** system
interfaces. Rust has built components directly since 1.82
(`--target wasm32-wasip2`, Tier 2), and the Wasmtime we already ship implements
both (`wasmtime-wasi` 49).

We want a developer to take an ordinary crate, build it with one command, and
call its functions from their app's script, with no glue and no new trust. A
component reaches only what its app may already reach.

## Decision

1. **Components beside modules.** A bundle's `fns/*.wasm` may be a component
   or a core module. The runtime tells them apart by the preamble
   (`component::is_component`). Modules keep ADR 0011's contract. A component
   is built with plain `cargo build --target wasm32-wasip2`.
2. **Typed functions, called with JSON.** Every function a component exports is
   callable from the app's script with no glue:
   - A world's own functions are called as `wasm.<function>`, and functions in
     an exported interface as `wasm.<interface>.<function>`.
   - `wasm.functions` lists each one with its WIT signature.
   - Arguments are an object keyed by parameter name, an array in parameter
     order, or, for one parameter, the value itself.
   - WIT types map to JSON:
     - a record is an object, and a tuple is an array;
     - a variant is `"case"` or `{"case": value}`, an enum is its name, and
       flags are a list of names;
     - an option is `null` or the value, a `char` is one character, numbers are
       range-checked, and `list<u8>` is base64 text (an array of numbers is also
       accepted).
   - A function's `result<T, E>` return is its value, or the call's error with
     `E`.
   - Functions that take or return a resource are not callable from scripts.
     They're listed as skipped, with the reason.
3. **Instances keep their state.** One instance per component lives for as long
   as the app's worker, so a component can hold a document, a cache or a model.
   A trap or a deadline spends it; the next call gets a fresh one. An update, a
   grant change or a withdrawal discards it, as for modules.
4. **WASI scoped to the app's grants.**
   - **Always:** `wasi:clocks`, `wasi:random`, `wasi:io` and `wasi:cli`.
     stdout and stderr become the app's log lines (bounded). The environment,
     arguments and stdin are empty.
   - **`wasi:filesystem`:** only with the app's `storage` capability. Its
     storage folder is preopened as `/`, read-write, and nothing else of the
     host's filesystem is visible. Without the capability there are no
     preopens.
   - **`wasi:http` outgoing, phase 3:** only to the hosts in the manifest's
     `network.hosts`, through the shell's network policy.
   - **Never:** `wasi:sockets`, and any import outside these WASI packages. A
     component that asks for one is refused when it loads
     (`LoadError::Import`) and by App Hub's gate.
5. **No WIT to write.**
   - **Guest SDK, phase 2:** a guest crate, `octosense-component`, with an
     `#[octosense_component::export]` attribute that derives the WIT world from
     ordinary Rust signatures. These include numbers, `String`, `Vec<T>`,
     `Vec<u8>`, `Option`, `Result<T, String>`, and structs and enums marked for
     export.
   - **Tooling, phase 2:** App Flow's `octo` gains:
     - `octo wasm new`, which writes a crate template;
     - `octo wasm build`, which builds it, checks its imports against the
       manifest and writes `fns/`;
     - `octo wasm doctor`, which names dependencies that cannot build for
       `wasm32-wasip2` (C libraries such as `openssl-sys` or `libsqlite3-sys`,
       threads, multi-threaded runtimes) and suggests replacements.
   - **Distribution:** the SDK goes on crates.io (with the maintainer's
     approval), and until then on a git dependency.
6. **Admission sees what a component reaches.** App Hub's gate reads each
   component's imports:
   - it refuses any outside the allowed set;
   - it requires `storage` for `wasi:filesystem` and `network.hosts` for
     `wasi:http`;
   - it tells reviewers what the component reaches, for example "files in its
     app folder; HTTPS to api.example.com".
   Components need a new app contract version.

## Phases

| Phase | Scope |
| --- | --- |
| 1. Runtime spike (done here) | `crates/wasm-host::component`: load, check imports, list exports with WIT signatures, long-lived instances, JSON calls, the WASI subset above with the storage preopen, the deadline, the memory cap and logs. Tests run an unmodified crate (`pulldown-cmark`) built with plain cargo, and refuse a component that imports `wasi:sockets`. |
| 2. Usable by developers | The shell's `wasm` service: loading components from `fns/`, `wasm.<function>` calls, per-app instances, the storage grant from the manifest, and storage quota accounting for component writes. A larger input limit for components. The guest SDK and its macro; `octo wasm new/build/doctor`; App Hub's gate check and contract version; docs and an example app. |
| 3. Reach and platforms | `wasi:http` outgoing under `network.hosts`; an `octosense:host` import for host services under the same checks as `host.request`; compiling at install time, so a phone skips the first compile; Pulley (Wasmtime's interpreter) on iOS and, until its JIT policy is known, OpenHarmony; Windows once its CI runs the runtime's tests. |
| 4. Shared components | Reviewed, versioned components in App Hub's catalog that apps depend on, like npm packages. The installer verifies them, and every app still gets its own instance and grants. |

## Alternatives considered

- **Stay with core modules and JSON (ADR 0011 as it is).** It stays safe, but
  few crates run as they are, and every type is hand-encoded.
- **A WASI 0.1 (preview 1) module ABI of our own.** It gives files and clocks,
  but no typed interfaces and none of the component tooling. Rust's
  `wasm32-wasip2` builds components by default.
- **Native Rust loaded into the shell** (dynamic libraries, or JIT-compiled Rust
  such as makepad's Relax). It's fast and complete, but the code runs in the
  shell's process with its privileges. Relax is tracked as an experiment, and
  third-party code needs isolation first.
- **A Wasm runtime of our own, or wasmi.** Wasmtime is already linked, compiles
  with Cranelift, and implements WASI 0.2 and the component model.

## Consequences

- **The shell's dependency graph grows.** It gains `wasmtime-wasi` 49.0.2
  (`p2` only) and the `component-model` feature. Both are linked wherever
  `wasm-host` already is (feature `wasm-functions`).
- **A component reaches only what its app could already reach:** its own
  storage folder (with `storage`), and in phase 3 its declared hosts. Clocks
  and randomness are new to Wasm but available to every script.
- **Persistent instances use memory for longer.** The per-app worker cap
  (`MAX_WORKERS`) and the memory cap bound it, and idle workers exit as today.
- **Spike sizes:** `notes` (with `pulldown-cmark` and `getrandom`) is 310 KB;
  the sockets probe is 123 KB. Timings are not measured yet; phase 2 records
  them as ADR 0011 did.

## Open questions

- Quota for component writes: account each write (by wrapping the filesystem
  host) or check after each call. Phase 2 decides by measuring.
- Whether a component may call host services that open sheets (sign-in,
  review). Probably only through the script, never from a component's call.
- Async functions (WASI 0.3) and streaming bodies: after phase 3.
