# 组合 Mail 卡片：草稿、聊天与宿主审批

[English](mail-composable-cards.md) | 简体中文

原生 **Chat / Reply** 工作区共用一份已保存草稿。在隔离的 OnePlus 6 手机测试中，实际的 `deepseek-v4-flash` 与 `MiniMax-M3.1-Flash-Preview` 都通过聊天修改了预约时间，Reply 和最终审核显示完全相同的已保存正文。较早的受控物流演示也完成了用户实体批准和已验证的真实线程回复。这是不同验证阶段：本次新工作区测试没有发送真实邮件。本轮只有 Android 实体触摸屏输入可以批准发送；桌面／无障碍审批及完整手机 UI 矩阵仍未完成。

生成的卡片描述展示。Rust 宿主代码拥有账户、原邮件、已保存草稿、修订号和发送操作。编辑字段会更新持久化草稿；生成的 Review reply 按钮只打开宿主审核。模型和卡片本地的 `sent` 状态都不能授权 SMTP。

## 回复工作区设计与当前验证

旧交互有两个相互竞争的文档：assistant 建议的文字与真正保存的回复。因此它可能声称“已修改”，审核却仍读取旧正文。现在，原生聊天中用户要求的修改会通过绑定修订版的宿主凭证更新已保存草稿；assistant 的成功话术本身不能更新 UI。

| 时刻 | 用户看到的内容与操作 | 宿主行为 |
| --- | --- | --- |
| 打开 Mail 卡片 | 独立全屏工作区，Chat 与 Reply 位于底部操作区域 | 不绘制后台 Glance 信息流；保留发布时绑定的账户、邮件、草稿与线程 |
| 请求修改 | 键盘上方固定且可增高的输入框，聊天记录独立滚动 | 提供当前已保存草稿；编辑工具只保存匹配的修订版 |
| 模型完成 | 保存模型修改后显示“Reply updated · saved” | 使用权威草稿状态，不从模型文字推断成功 |
| 阅读或编辑 | 收件人、主题和可读正文；Edit 打开原生字段 | 输入先暂存，合并空闲保存；切换 Chat 前保存 |
| 对照原邮件 | View original email / Back to reply | 读取绑定的原邮件，不替换回复 |
| 审核与发送 | 独立最终审核显示 From、To、主题和准确正文 | 只有实体 Approve & Send 批准该不可变载荷 |
| 保存冲突 | 保留未保存文字，提供 Use my edit / Use saved reply | 不静默覆盖较新数据，解决冲突前阻止聊天／审核 |
| 发送中或结果不确定 | 明确显示发送中、已接受、失败或未知 | 保留回执；明确重试必须重新审核、批准 |

聊天采用虚拟化 `PortalList`、段落行和独立原生 `TextInput`；Reply 有自己的可滚动预览／编辑器。输入与滚动都不会重新生成 L0 聊天布局，打开原生 Mail 也不再构建用不到的生成布局。标签和主要操作至少有 44 点点击区域；键盘出现后，正文获得剩余的编辑空间。

**双模型检查点（Lab 0427）：** 关闭备用模型。保留原有 DeepSeek 生成的 L0 源码，SHA-256 为 `5186f14c6e692dfc63af20d788876630cdde6e381411404fd3a7d7d765e2ed30`。只把隔离测试的权威邮件／草稿换成虚构预约，没有复制 Gmail 凭据。两家模型收到相同要求：把周二下午 3 点改为周三上午 10 点，其余不变。它们都真实调用 `mail.suggest_reply`，收到 `applied: true`，把完全符合预期的正文保存为修订版 2。正文由模型修改；评估者操作手机 UI，核对存储、工具记录和截图。

两家的最终审核载荷均与修订版 2 正文一致；注入批准被拒绝，取消后回到草稿。DeepSeek 的修改经重启保留。随后原生编辑器保存备注为修订版 3，MiniMax 从 Chat 正确读出新备注，没有改写或发送邮件。这验证了工作区的双向连接，不是一次新的自主新邮件测试，也不是受控模型质量比较。

**最终布局／性能检查点（Lab 0429）：** 实机截图覆盖 Chat、Reply 和键盘上方输入框。短时热态滚动窗口的帧间隔 p95 为 17.5–18.4 毫秒，持续活动窗口约 57–59 fps。首次打开／切换窗口仍包含 300–380 毫秒停顿；这仍是性能限制，热态指标不能代表冷启动。Lab 0431 还检查了长收件人和主题：元数据在两行内换行，并明确显示省略号；次要按钮获得焦点后仍保持正确配色。最终独立用户测试包为 0432，使用相同生产代码，安装前后的活动卡片、草稿、聊天记录和 agent 策略逐字节一致，没有注入真实草稿修改或聊天提交。

**本地验证：** 905 项 shell、53 项 Mail 服务及 12 项上下文聊天测试通过；两项既有环境依赖 Mail 测试仍忽略。原生 Makepad 绘制测试覆盖 200 条聊天记录、键盘缩放、可见输入框／审核按钮和延迟布局。服务测试覆盖过期、重放、错误作用域凭证，并发人工修改、旧审核撤销以及聊天不执行 SMTP。桌面默认／mobile-apps 检查、手机检查和 Android 构建通过。这些不能替代实机输入法、无障碍、账户切换、存储失败或不确定发送结果的验收。

**导航修订（Lab 0433）：** 实机截图验证了 Reply、Chat 及键盘上方的底部操作组合。905 项 shell 测试及桌面／手机检查通过。0434 将同一布局安装到独立用户测试包，保留真实卡片、草稿、聊天记录与策略。本次导航修订没有重复模型调用或 SMTP。

**重新开启 UX 验收，撤回此前的 9.0／10 评分。** 原审查把功能正确误当成易用性，漏掉了顶部模式标签与底部编辑／审核按钮之间的频繁往返。模型和存储测试结果仍成立，但不能证明 UX 达标。本次不另给一个未经充分验证的数字评分。

修订后的 Mail 布局把 Chat / Reply 放在底部操作区域，与当前页面的输入框或 Edit / Review 操作相邻；键盘出现后仍保持这个组合。去掉重复的 View reply 按钮，把原邮件入口移到邮件元数据旁边。保存完成用简短状态说明，不再增加一个导航控件。最终发送审核仍是独立步骤，批准准确的邮件内容。

验收必须检查真实的重复任务是否顺手：要求改时间、切到 Reply、手工编辑、回到 Chat、进入审核并返回。除了保存数据、键盘可见性和性能，还要检查手部移动、控件分组和视觉层次。自动几何检查只能证明控件画在哪里，不能证明单手操作舒适，也不能代替实际使用者的反馈。

## 沿代码追踪一封回复

原生工作区现在使用 **Chat / Reply**。Reply 通过 `mail_clip::MailClip` 读取权威草稿；输入暂存在 `mail_card::Session` 中，停止输入 500 毫秒后保存，进入 Chat 或审核前立即保存，冲突时保留未保存文字。原生聊天可为显示的账户、草稿和修订号签发五分钟有效的一次性正文编辑凭证。带有该 `edit_token` 的 `mail.suggest_reply` 会保存用户要求的修改，并返回 `applied: true`；没有凭证时，后台建议仍需明确接受。只有已保存的宿主状态才能显示“Reply updated”，模型的文字不能充当保存确认；两条路径都不发送邮件。修订后的契约见 ADR0007 的原生聊天例外。下方较早的设备验证记录针对旧的接受建议流程。

1. 传入事件分发器在已登录账户下启动 Mail 应用 agent。agent 读取邮件，然后调用 `mail.propose_reply`，提供 `message`、可选 `folder` 和建议的 `body`。[Mail 服务](../apps/mail/host-service/src/drafts.rs)推导收件人与回复邮件头，返回 `draft_id`、`revision` 和 `chat_thread`。`mail.draft` 读取已保存修订版；`mail.suggest_reply` 创建绑定修订版的建议，或消耗原生聊天的限定编辑凭证；`mail.propose_send` 准备不可变提议，不执行发送。
2. `mail.publish_card` 接收该 `draft_id` 及模型编写的 L0 源码／数据。[发布路径](../crates/shell/src/glance.rs)在生成数据之外附加可信 Mail 元数据，拒绝把已绑定卡片改指向另一个账户、邮件或草稿。普通 `glance.publish` 不能提供此绑定。
3. [卡片适配器](../crates/shell/src/mail_card.rs)从宿主存储回答 `sys.mail_draft(app, id, fields)`。可写源只声明 `to`、`subject`、`body` 中的一个；直接绑定的 `Field(text: draft.body, on_change: save)` 配合 `draft: set($value)` 携带 Field UserInput。适配器保存前校验显示中的修订号。冲突或失败的编辑仍作为可见的未保存输入保留，不会静默接受。
4. `sys.chat(app, thread, fields)` 使用宿主返回的线程。[聊天适配器](../crates/shell/src/glance_chat.rs)把绑定的邮件、持久化草稿修订版和有限线程历史交给 Mail 现有 peer。未保存文字不包含在内。过期 agent 建议不能覆盖后来的编辑。这是同一账户 peer 内的对话上下文，不是另一个内核或应用 agent。
5. `sys.mail_review(app, id, fields)` 的 `set` 请求审核，`clear` 取消审核。[展开卡片](../crates/shell/src/glance_sheet.rs)内的[宿主审核 UI](../crates/shell/src/mail_review.rs)显示准确账户、收件人、主题和正文。只有其可信 Approve & Send 手势，才把不透明的审核能力交给服务执行器。agent 没有 `mail.send` 或 `mail.approve`。完整应用的旧发送入口也会请求宿主审核；开发者模式不能绕过该检查。
6. 服务取得不可变操作的执行权，并在 SMTP 前记录身份。重复请求共享已有结果。`accepted` 表示 SMTP 接受，不等于收件人收到。不确定结果绝不自动重发；明确重试需要重新批准新的尝试，适用时还要确认重复发送风险。卡片／聊天发布失败，不能把本地状态变化变成投递回执。

完整决策与强制验收条件见 [ADR0007](adr/0007-composable-mail-action-cards.zh-CN.md)。初期回复仅支持一个经审核的 To 地址；Cc／Bcc、全部回复、附件、富文本和转发仍不支持。

草稿和尝试回执会持久化；审核能力刻意不持久化，重新打开后必须重新审核、批准。完整写信界面在活跃会话内保留 compose ID，但目前没有已保存草稿列表，无法在重启后任意选择草稿重开。宿主私有发布缓存只为当前已登录账户、且仍有权威已保存草稿的卡片恢复模型 Glance 源码／数据。它保留原始到期时间（digest 到期可能进一步缩短它）以及持久关闭／撤销状态，不再发送通知。5 个缓存测试和 27 个 Glance 测试已通过。下述 DeepSeek 真机检查也确认进程重启后保留已保存正文和卡片；这不代表所有账户切换、到期或关闭路径均已完成真机验证。

生成的视图使用显式枚举比较（`when mode == .brief`），并保证初始分支可见、
深入视图有可达的返回操作。裸写 `when mode` 只接受布尔值 `true`。
聊天输入的 `on_change` 仅更新本地文字，`on_commit` 才追加完整问题；
每次按键都追加聊天会发送不完整内容，并可能触发线程的限流或忙碌限制。
回复正文使用 `on_change` 保存，不设置 `on_commit`，由宿主呈现为多行编辑器。

完全相同的 `mail.publish_card` 参数复用持久化回执，不再次通知。
以相同卡片和草稿 ID 提交修正后的源码或数据，会重新验证和发布，并遵循
请求中的 `notify` 值。没有参数指纹的旧回执允许一次经过验证的刷新。


## 运行时契约与输入来源

[工具 schema](../apps/mail/bundle/tools.json)定义四个草稿／提议工具。目录契约固定在 Octoscript `2e37d9e657a246f16718d9a475e167ccd2d5b5fa`，Octoscript-Makepad 固定在 `27e9c1bfdbf6021bcad87214ae4ebbe6d683b406`。两个 Mail 源都要求应用身份为字面量；本宿主还要求草稿 ID 字面量与可信发布绑定一致。检查器将草稿 `to`、`subject`、`body` 和 `suggestion_body` 保守地视为模型文本：可以显示／编辑，不能直接复用为操作载荷或源选择参数。宿主批准授权准确的已保存邮件，不要求用户把未经修改的 AI 草稿重新输入一遍。

下文的历史真机运行对应 **0416**（`abf06d8f`），当时使用 Octoscript `9ca9545b` 和 Octoscript-Makepad `a950f7fb`。当前固定版本仅对同一份 L0 实现应用 rustfmt，并将该修订同步到包装层。较新的 0427–0432 工作区版本使用当前固定版本，其验证单独记录在上方。

[Makepad 补丁](../tools/runtime-patches/makepad-trusted-user-input.patch)默认令 `trusted_user_input()` 为 false。Android JNI 检查正数且非虚拟的设备 ID、触摸屏来源、未遮挡标志及非取消输入；空对象或 Java 异常不会入队可信输入。作用域 guard 只在原生 TouchUpdate 处理器执行期间生效。远程／嵌套模拟分发、延后的 action 和脚本任务不能继承它。宿主审核要求相匹配的可信按下与释放。`with_untrusted_input` 只能移除信任。目前键盘／输入法、长按、桌面和无障碍输入都不能批准发送。受攻击的 OS／root 进程冒充硬件，不在这一应用级边界内；这不是硬件认证。

### DeepSeek：通过的操作与修正过程

一封测试邮件触发使用 `deepseek-v4-flash` 的 Mail agent 自主处理并创建回复草稿，
卡片源码由模型编写。
初始运行尝试发布 13 次；最终通过语法检查的卡片只显示标题，因为它把枚举
