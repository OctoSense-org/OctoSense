# 桌面账户写入审批

[English](os-authenticated-approval.md) | 简体中文

Linux 和 Windows 在原生审阅页发送 Gmail、保存 GitHub 文件或 Calendar 日程、执行已声明
的后端变更时，增加独立的 OS 认证步骤，具体设计见 [ADR 0013](adr/0013-os-authenticated-write-approval.zh-CN.md)。
这两个平台上，由用户实际完成认证再执行业务写入的正向验收仍**未经验证**。适配器编译或
浏览器登录通过，不能替代这项证据。

应用准备修改并打开现有宿主原生审阅页。用户检查账户、目的地和完整内容，选择
**Authenticate & Send（认证并发送）** 或 **Authenticate & Save（认证并保存）**，再完成
OS 认证。OctoSense 只接收结果，不接收 PIN、密码或生物识别信息。合成点击可以发起认证
请求，但自身不能批准写入。macOS 和 Android 保留现有的物理输入审批路径。

## 平台要求

Linux 需要系统 polkit authority、用户桌面会话中的认证 agent，以及完全匹配的 OctoSense
策略。`.deb` 打包配置将 `desktop/resources/org.octosense.policy` 放入
`/usr/share/polkit-1/actions/org.octosense.policy`。活动会话使用不保留授权的 `auth_self`，
其他或非活动会话拒绝。宿主检查文件内容、root 所有权以及组/其他用户不可写；缺少或
改变策略、缓存授权、取消、认证 agent 不可用均拒绝。它不启动特权命令。

AppImage 与源码用户需要管理员将完全相同的策略文件安装到该系统路径，所有者为 root，
普通文件权限为 `0644`。OctoSense 不执行这项安装。共享验收机**没有执行**管理员策略安装
或成功的 polkit 对话框认证。打包映射已有测试，但这不能证明安装后的桌面会话能够批准。

Windows 桌面 Windows Hello 接口要求 build 22000 或更新版本，以及已配置并启用的验证方式。
OctoSense 先检查可用性，再将提示绑定到准确的宿主 HWND；只接受原生 `Verified` 结果。
旧系统或未配置的系统显示不可用，不退回普通确认按钮。

## 审批绑定内容

一次性证据仅由原生 Rust 持有，绑定已接纳的包与权限、连接与账户代次、审阅 ID、原生窗口
代次和宿主页所有者。规范化操作摘要包含完整变更，包括 GitHub 预期文件 SHA、Calendar
事件 ID、etag 和创建 ID。认证期限最长 120 秒，不能延长原审阅期限。

取消、修改草稿/账户/包、超时、窗口复用或重复结果均拒绝。提交线程获得每应用执行锁后，
再次检查期限和授权；后端变更在令牌刷新后、业务请求前再次检查。取消审阅不会撤回已经
开始执行的提供商请求。

审阅页检查绘制边界与原生所有者。待处理挑战仅在定时器或完成信号时检查，不在每次鼠标
移动时重复检查。OS 认证可以从应用接管焦点，因此失去焦点既不是批准证据，也不能成为
把合成输入视为可信输入的理由。

## 验收边界

确定性测试覆盖一次性声明、迟到结果、取消、账户/包/摘要/窗口变更、原资源版本，以及排队
等待账户操作锁期间超时或撤销的审批。Linux 原生测试还验证实际适配器在缺少系统策略时
不能启动审批；测试不安装系统策略。

可选 Windows 可用性测试调用真实 OS API，但不请求身份验证，只记录可用性或 API 拒绝；
`Available` **不代表**认证审批通过。Windows 工作流执行该测试及适配器拒绝/取消测试。

仍**未经验证**：用户完成 polkit 或 Windows Hello 对话框、成功执行准确审阅的合成业务写入、
在对话框显示时由用户取消。这些检查需要正确配置的桌面与实际用户。浏览器登录、凭据库
持久化和平台输入来源验证分别记录验收结果。
