# WebAssembly in OctoSense

English | [简体中文](wasm.zh-CN.md)

WebAssembly turns up in four places in OctoSense. One is designed to run an
app's own code: an app's own functions, which standard builds run on macOS,
Windows, Linux, Android and OpenHarmony, with limited support. The plug-ins of two engines,
photocraft behind `photo` and vectorcraft behind `vector`, are closed: both
services refuse every plug-in command. The other two are a makepad internal and a browser build that does not compile.
For each, this page says whose module runs, what it can reach, which builds
have it and how it was checked. This page describes the current source tree.
Desktop 0.1.0-rc.2 contains ADR 0011 core modules, not ADR 0014 components or
the declaration-only changes below. Source, test and release status are separate.
See [capabilities and execution boundaries](capabilities.md).

## An app's own functions: the `wasm` service

[ADR 0011](adr/0011-apps-own-functions-in-webassembly.md) (Accepted, with
limited support) lets an app ship Rust functions compiled to WebAssembly in
its bundle, and the shell runs them for that app only. They are for light
computing beside a script: parsing, ranking, scheduling, diffing, a format
conversion. Splash's compute kernels stay the answer for numeric work.

### The module

A module is core WebAssembly at `fns/<name>.wasm`, at most 8 per bundle, with
no WASI. A file there may instead be a [component](#components), which has
both.

- It exports `memory`, `octo_alloc(len) -> ptr` and `octo_free(ptr, len)`.
- Every other export of type `(i32, i32) -> i64` is a function: it takes its
  input at `(ptr, len)` and returns `(out_ptr << 32) | out_len`. The output
  starts with a status byte, `0` for success and `1` for an error, whose text
  follows.
- Its only import may be `octo.log(ptr, len)`. A module that imports anything
  else is refused when it loads.
- It has one memory and at most one table.

The guest crate
[`apps/wasmlab/guest/octosense-guest`](../apps/wasmlab/guest/octosense-guest/src/lib.rs)
writes all of this: `export!` for `fn(&[u8]) -> Result<Vec<u8>, String>`,
`export_json!` for serde types, and `log`. Build the crate as a `cdylib` for
`wasm32-unknown-unknown`. Builds for `wasm32-wasip1` and wasm-bindgen output
import functions the shell does not provide, so they do not load; a build for
`wasm32-wasip2` is a [component](#components), the other kind it runs.
App developers start from App Flow's
[Run your own Rust code](https://github.com/OctoSense-org/OctoSense-App-Flow/blob/main/docs/RUST.md).

### Components

[ADR 0014](adr/0014-app-components-in-webassembly.md) (Accepted; rollout incomplete) adds a second
kind of `fns/<name>.wasm`: a WebAssembly component, built from an ordinary
Rust crate with `cargo build --target wasm32-wasip2`. The service tells the
two kinds apart by the file's preamble, and a bundle may carry both.

- **No glue.** Every function the component exports is `wasm.<function>`,
  named in snake_case: `save-html` is `wasm.save_html`, and either spelling
  is accepted. Arguments are an object keyed by parameter name, an array in
  parameter order or, for one parameter, the value itself. A record comes
  back as an object, an enum as its name, `list<u8>` as base64 and a
  `result<T, E>` as its value or the request's error. `wasm.functions` lists
  every export with its WIT signature; a function that takes or returns a
  resource is listed as skipped, with the reason.
- **State.** Each component's instance lives on in the app's worker between
  calls, so it can keep a parsed document or a cache. A trap or the deadline
  spends it and the next call gets a new one; an update, a changed grant, a
  withdrawal or the worker's exit (a minute without calls) ends it.
- **What it reaches.** Clocks and random numbers. Its stdout and stderr become
  the app's log lines, and it gets no environment, arguments or stdin. A
  component that imports anything beyond `wasi:cli`, `wasi:clocks`,
  `wasi:filesystem`, `wasi:http`, `wasi:io`, `wasi:random` and
  `octosense:host`, such as sockets, is refused when it loads.
- **Files.** The app's available storage folder, the one its script's `fs.*`
  sees, is the component's `/`. Account-scoped apps need their active account.
  Nothing else on the device is visible. Missing storage or a signed-out
  account leaves no preopen; omitting the `storage` declaration does not.
- **The storage quota.** A call may add what is left of the app's quota when
  the call starts. A write past it fails inside the component: `ftruncate`
  reports a full disk, and an ordinary write an I/O error, because wasi-libc
  reports any failed stream write as one. The request's error then ends with
  "a write was refused: the storage budget is used up". Rewriting, truncating
  and deleting give bytes back, so a component can free space.
- **The network.** Its `wasi:http` requests reach any host, as the device
  can: an app's network declarations (`net`, `network.hosts`) are shown when
  it is installed and not enforced while it runs. The ruling of 8 October
  2026 removed the per-app runtime gates; the OS and the host's API surface
  are the boundary. The pinned Splash runtime also no longer enforces the
  manifest host list. A component that
  imports `wasi:http` gets 10 s a call instead of 2 s, and each request's
  connect, first-byte and between-bytes timeouts end with the call.
- **Host services.** Through `octosense:host`
  ([`crates/wasm-host/wit/octosense-host.wit`](../crates/wasm-host/wit/octosense-host.wit)),
  `request(service, args)` uses the admitted app's identity, dispatched on
  the UI thread. Declaration lists do not gate the call. Each service still
  checks its account, consent, review and resource boundaries. A component
  never gains a sheet, prompt or trusted user input, so only methods a
  background surface may call are available. `wasm.*` is refused, since the app's worker is busy with
  the call, and the call's deadline bounds the wait.

ADR 0014 records what this costs. On an M-series Mac, the 313 KiB test
component compiles in about 40 ms and loads from the cache in about 4 ms;
its Markdown function runs about 2.6 times slower than native Rust, close to
the same code as a module. In Pulley it runs about 32 times slower than
that.

### Shared components

An app can also call a component that App Hub publishes on its own (App Hub
ADR 0003, OctoSense ADR 0014 phase 4). The manifest pins it under
`components` by alias, id, exact version and BLAKE3 digest, and requires
`wasm-shared-components-v1`. The `wasm` service loads each pinned component
beside the app's `fns/` and routes its functions as `wasm.<alias>.<function>`:
with `{"as": "md", "id": "org.example.markdown", …}`, `wasm.md.to_html` calls
the component's `to-html`. The app gets an instance of its own, under its own
account and storage boundaries, as for a component in its `fns/`. It may carry no `fns/` at all and
call only shared components. `wasm.functions` lists their functions with the
alias, and names the component each comes from (`"shared": {"alias", "id",
"version", "blake3"}`).

The service asks App Hub for the files on every load
(`octosense_appstore::components::resolved_in`). A system app's are in its
bundle at `components/<blake3>.wasm`. An installed app's are in the shared,
read-only store at `<apps root>/.components/<blake3>.wasm`. Each is checked
against the verified catalog, which must still offer it at that version, and
against its digest. Nothing is fetched there: App Hub's installers fetch an
app's components before the app itself. A missing, changed or withdrawn
component stops the app's launch.

`wasm_service::tests::a_pinned_shared_component_answers_as_alias_and_function`
runs this path with a stand-in resolver. No catalog has published a component
yet, so installing an app that pins one and calling it in a shell is
**unverified**.

### How a module reaches a device

- **A store app.** App Hub's current gate (app contract 1.11) admits up to
  8 `.wasm` files at `fns/<name>.wasm` (name `[a-z0-9_-]`, at most 64
  characters). It distinguishes core modules from components and checks
  component imports and required ABIs. It verifies exact shared-component
  versions, digests and publishing proofs. Omitting `wasm`, `storage` or
  `net` is not an admission refusal. Keep those declarations accurate for
  store disclosure; the runtime still validates code when it loads.
  The rules are in App Hub's
  [publishing reference](https://github.com/OctoSense-org/OctoSense-App-Hub/blob/main/docs/PUBLISHING.md)
  (the `functions` finding and the `wasm` capability).
- **A system app.** It is packed into the shell like any other, by digest,
  from the packaging's system-app list. `desktop/system-apps-wasm-lab.json`
  and `phone/system-apps-wasm-lab.json` are the standard lists plus `wasmlab`.

### The service

The `wasm` host service (`crates/shell/src/wasm_service.rs`) is in every
standard desktop and Home build on macOS, Windows, Linux, Android and
OpenHarmony: the shell's `wasm-functions` feature, on by default in both
packages (`wasm-lab` is its former name). iOS leaves the runtime out. A build
without the service answers `no service answers "wasm" on this device`.
It answers two kinds of request:

- `wasm.functions`: the functions the app's modules export, how each module
  loaded (compiled, or from the cache, and how long it took) and how each
  function has run.
- `wasm.<function>`: one call. For a module, a string argument goes in as its
  text and anything else as JSON; JSON output comes back as data, anything
  else as `{"text": …}`. A component's arguments and result are typed
  ([Components](#components)). The function's own error, a trap or the
  deadline is the request's error.

The code always comes from the calling app's own admitted, digest-checked
bundle, never from an argument, and no app reaches another app's functions.
The service rechecks bundle admission and app/profile identity before loading
or executing code. Capability declarations do not authorize execution.

Every call to a module gets a fresh instance: memory, globals, tables and log
lines from one call never reach the next, including after a success or the
function's own error. A component keeps one instance between calls instead
([Components](#components)). Only compiled code is reused, in the app's worker and in a disk
cache (`wasm-cache` in the host directory, keyed by the module's SHA-256 and
the engine's compatibility hash). The service checks admission again before a
call runs and before its answer is delivered. An update, a changed grant or a
signed withdrawal discards the answer and the compiled code. Compiling cannot
be interrupted, but an expired or cancelled request never goes on to run.

| Limit | Value |
| --- | --- |
| One call, start function included | 2 s of wall-clock time (checked every 10 ms) |
| Linear memory | 256 MiB |
| Table elements | 16,384 |
| Wasm stack | 512 KiB |
| Module | 8 MiB |
| Input or output of one call | 16 MiB in the runtime; 8 MiB of serialized input in the service |
| Log | 64 lines a call, 1 KiB each |
| Modules per app | 8 |
| Apps running functions at once | 4 workers, one per app |
| Queued requests | 4 per app |
| Buffered input, all apps | 32 MiB |
| One request, queueing and loading included | 10 s |
| An idle worker | exits after 5 s, or after 60 s while it holds a component's instance |

A full queue or no free worker fails the request at once instead of making it wait.

When App Hub installs or updates an app, the shell compiles its functions into
the cache in the background (`wasm_service::warm`): one app at a time, on a
thread of its own, from the admitted bundle. The
app's first call then loads from the cache instead of waiting for Cranelift.

### Agent tools

An app's `tools.json` may map a tool to one of its functions with
`"host_method": "wasm.<function>"`. The tool must be offered by its app; a
`wasm` declaration is not an execution grant. Unlike
shared host methods it has no minimum risk and needs no
`"private_data": true`: a module sees only the arguments it is given, and a
component also its own app's folder, as the app's script does. Neither
reaches shared data. Wasm Lab maps `wasmlab.find_slots`, `wasmlab.rank` and `wasmlab.diff`
to `wasm.find_slots`, `wasm.fuzzy_rank` and `wasm.text_diff`, all `read`.

### Wasm Lab

Wasm Lab (`os.wasmlab`, `apps/wasmlab/`) is the system app that shows the
service. It is a demo: standard builds do not ship it. Its functions
(`apps/wasmlab/guest/functions`) are Markdown to HTML (pulldown-cmark), free
slots around busy times, fuzzy ranking (strsim), a line diff (similar), and
`rogue`, which loops forever, allocates without end, panics or recurses
without end on request. Its screen calls each one through `host.request` and
shows what came back, the round trip and `wasm.functions`.

Build a desktop with it, then start it with Wasm Lab open, hidden and driven
over the remote control surface (`/help` lists the routes; end with `/quit`):

```sh
OCTOSENSE_SYSTEM_APPS=$PWD/desktop/system-apps-wasm-lab.json cargo build --locked -p octosense
MAKEPAD_HIDE_WINDOWS=1 target/debug/octosense --remote=47631 --test-action launch-wasmlab
```

On the Linux build host (8 October 2026; a default debug build, hidden, under
a headless Weston), the module compiled in 98 ms on first use and loaded from
the cache in 4 ms after that, also after a restart. Each misbehaving mode
ended in an error and the shell kept running: the endless loop at its deadline
after 2,039 ms, endless allocation at the memory cap after 340 ms, and the
panic and runaway recursion after 37 ms each, as the script timed them.

When it opens, Wasm Lab makes its four calls first and asks for
`wasm.functions` once they have answered: the service queues at most four
requests per app. `wasm.functions` counts calls since the app's worker
started; a worker exits after five idle seconds, and the counts start again
with the next one.

The checked-in module rebuilds byte for byte: with rustc 1.97.1,
`apps/wasmlab/guest/build.sh` writes the same `bundle/fns/wasmlab.wasm`
(SHA-256 `f4a69c32…`). It needs the target once:
`rustup target add wasm32-unknown-unknown`.

### Tests

```sh
cargo test --locked -p octosense-wasm-host
cd phone && cargo test --locked --features mobile-apps -p octosense-shell wasm_service::tests
```

- `crates/wasm-host/tests/runtime.rs` runs a hand-written guest: input and
  output, guest errors, the deadline, the memory, table and stack caps, traps,
  the import rule, per-instance state, threads, the size limit, the cache and
  its concurrent writers, cancellation.
- `crates/wasm-host/tests/guest.rs` runs Wasm Lab's module and compares every
  function with the same Rust run natively, then every `rogue` mode.
- `crates/wasm-host/tests/component.rs` runs four components built from
  `crates/wasm-host/tests/component-guest`: an unmodified crate
  (pulldown-cmark) called with JSON, records and snake_case names, state
  kept on one instance, clocks, randomness and bytes, files only in the
  app folder (also read-only), the storage budget, the deadline and the
  memory cap; `fetch`, whose `wasi:http` reaches a local server without a
  manifest host allowlist, and whose request to a server that never answers ends at the
  deadline; `hostcall`, which calls host services through the embedder; and
  a component that imports sockets refused.
- The service tests cover the tool mapping, bounded input, a fresh instance
  per call, revocation after an update, a grant change or a withdrawal,
  cancellation and the queue bounds, and the app's own functions answering
  its tools and its script. For a component they cover typed calls, its
  instance's state, the app's storage folder and its quota, an app without
  available storage area, a component shipped as a system app through App
  Hub's admission, network calls without a manifest allowlist, host calls
  under the app's identity and service boundaries, and an installed app's first call
  loading from the cache.
- `cargo run --release -p octosense-wasm-host --example measure_component`
  prints a component's timings against a module and native Rust.
- `OCTOSENSE_WASM_PULLEY=1 cargo test --locked -p octosense-wasm-host --features pulley`
  runs the same tests in Pulley, as OpenHarmony runs them; `phone.yml` runs
  it too.

The test components rebuild byte for byte: with rustc 1.97.1,
`crates/wasm-host/tests/component-guest/build.sh` writes the same
`notes.component.wasm` (SHA-256 `963c965b…`), `netprobe.component.wasm`
(`98b2402a…`), `fetch.component.wasm` (`6eaf6ac8…`) and
`hostcall.component.wasm` (`d39f2a8e…`). It needs the target once:
`rustup target add wasm32-wasip2`.

`phone.yml` runs the first command, and the service's tests as part of Home's
(`mobile-apps` includes `wasm-functions`); `tools/ci-local.sh --linux-host
--offload` runs both on the Linux build host. Every CI build of the desktop
and Home includes the service, and `tools/check-shell-graph.sh` checks that
its runtime is linked exactly on macOS, Linux and Android.

### Not done yet

- No release includes the service yet: the first desktop and Home releases
  built from `main` after #400 will.
- iOS: building Home for iOS with the service (in Pulley).
- CPU fairness between apps, and a bound on the disk cache, which nothing
  evicts.
- Compiling system apps' functions ahead: an installed app's are compiled at
  install, a system app's at its first call.
- Components on a phone: Android and OpenHarmony builds link the runtime,
  but no component has run on a device yet (**unverified**).
- Shared components end to end: no App Hub catalog has published one yet,
  so no installed app has pinned one (**unverified**).
- Bytes are slow through JSON: a 1 MiB `list<u8>` costs about 18 ms there
  and back, as base64.

## Engine plug-ins: the `photo` and `vector` services

Two engines of ADR 0013 host their own WebAssembly plug-ins, in wasmi, a
pure-Rust interpreter, each in a registry that belongs to the process, not to
a call:

- photocraft, the raster engine behind the `photo` service
  (`apps/photo/host-service`): filter plug-ins with no imports, 32 MiB per
  module, 512 MiB of memory per instance, 50 million instructions per call
  and 60 s per run.
- vectorcraft, the vector engine behind the `vector` service
  (`apps/vector/host-service`): object filters and live effects with no
  imports, a fuel budget, a memory cap and a fresh instance per run.

effectcraft, behind `effect`, has WebAssembly plug-ins too, behind an optional
feature; OctoSense does not link its plug-in crate. vectorcraft's desktop UI
crate has a second install command, `ui.installPlugin`; OctoSense does not
link that crate either.

**Closed since #398.** `photo.run` refuses every `plugin.*` command before the
engine sees it, and `photo.commands` leaves them out. Before #398 a caller
could install a plug-in from base64 `data`; it went into photocraft's
process-wide registry, outlived the call and served every later caller, under
limits far above the `wasm` service's. A scratch program that calls the
service as a script's `host.request` does showed both, on the Linux build host
(8 October 2026). Before #398, `os.photos` installed photocraft's example
plug-in, the next call listed it, and another system app, `os.notes`, ran it
on a document. With #398, each of those calls was refused. Since the
command doors (#418, ADR 0013) the refusal is the allowlist gate's, which
classes every `plugin.*` id `code`:
``photo.run: `plugin.install` is classed code: it installs or runs code, or runs other commands, so the door never runs it``.

**Closed in `vector` by #405.** `vector.run` refused files, documents, the
`app.*` group and path-like arguments, but not `plugin.*`, and vectorcraft's
engine installs a plug-in from base64 `dataBase64`. The same scratch program
showed it on `main` before #405: `os.notes` installed vectorcraft's example
plug-in, the next call listed it, another system app (`os.maps`) saw it, and
`vector.commands` offered `plugin.install`. Now `vector.run` refuses every
`plugin.*` id before the engine sees it (since #418 by the allowlist gate:
``vector.run: `plugin.install` is classed code: it installs or runs code, or runs other commands, so the door never runs it``),
and `vector.commands` leaves them out. An effect plug-in named to a built-in
effect command (`effect.apply {effect: "plugin.<id>"}`) is refused too.

Both engines still link wasmi, and both services answer system apps (`os.*`)
only.

**The UI thread.** The `photo` service, like the other engine services, does
its work inside the request. App Hub dispatches a script's `host.request` on
the UI thread, and calls the service while it holds the lock on the service
registry (`services::dispatch`). So a long `photo.run` holds up the UI and
every other app's requests until it returns
([#399](https://github.com/OctoSense-org/OctoSense/issues/399)).

## Splash math and compute kernels

makepad's script engine can compile a pure-math Splash function, such as a
signed distance field, into a WebAssembly module it generates itself, and run
it in makepad-stitch, its own interpreter, as the reference that matches the
Splash interpreter bit for bit
(`.sources/makepad/platform/script/src/math_aot/`). No app supplies that
module. In OctoSense only makepad's CSG library would call it, and OctoSense
does not link that library, so the code is present and unused. ADR 0011
measured stitch for apps' functions (2,942 CoreMark against Wasmtime's
44,534) and did not choose it.

makepad's compute kernels also have a WebAssembly backend, but it runs only
when makepad itself is compiled for `wasm32` (a browser). Native builds use
their native backends.

## The shell in a browser

The shell keeps the `wasm32` paths of makepad's window manager, its "web
superbuild": no child processes (`crates/shell/src/host.rs`), every native app
hosted in process (`tools/native_apps.py` gives each app a `wasm` hosting of
`module` or `none` in `crates/shell/src/native_apps.rs`, and refuses
`process` there), and in-process service links for the assistant
(`crates/shell/src/pane_links.rs`). App Hub reports such a host's platform as
`web`.

No build, CI job or release produces it, and it does not compile. This check
on the browser target fails:

```sh
cargo check --locked --keep-going --target wasm32-unknown-unknown -p octosense-shell --no-default-features
```

getrandom 0.2 and 0.3, uuid, fs2, ring and aws-lc-sys fail to build for that
target. Even without default features the shell links `octosense-ai-host` and
App Hub's crates, which bring in most of them (credential encryption, sigstore
verification, TLS, file locking); the shell's own `uuid` lacks a randomness
source there. Treat these paths as unmaintained.
