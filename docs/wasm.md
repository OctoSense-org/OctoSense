# WebAssembly in OctoSense

English | [简体中文](wasm.zh-CN.md)

WebAssembly turns up in four places in OctoSense. One is designed to run an
app's own code: an app's own functions, which standard builds run on macOS,
Linux and Android, with limited support. The plug-ins of two engines,
photocraft behind `photo` and vectorcraft behind `vector`, are closed: both
services refuse every plug-in command. The other two are a makepad internal and a browser build that does not compile.
For each, this page says whose module runs, what it can reach, which builds
have it and how it was checked. It describes `main` after #400 (8 October
2026).

| --- | --- | --- | --- | --- |
| [An app's own functions](#an-apps-own-functions-the-wasm-service): the `wasm` service ([ADR 0011](adr/0011-apps-own-functions-in-webassembly.md)) | The app's own bundle, `fns/*.wasm`, under the `wasm` capability | Wasmtime 49, compiled by Cranelift (`crates/wasm-host`) | Every standard desktop and Home build on macOS, Linux and Android (feature `wasm-functions`); none for Windows, iOS or OpenHarmony | Accepted, limited support. Tests pass on macOS and Linux; a OnePlus 6 passed the phone acceptance. No release has it yet |
| [Engine plug-ins](#engine-plug-ins-the-photo-and-vector-services): photocraft behind `photo`, vectorcraft behind `vector` ([ADR 0013](adr/0013-craft-engines-as-pinned-services.md)) | None: both services refuse every `plugin.*` command (#398, #405) | wasmi 2, an interpreter | Linked into every build with App Hub | Closed: no caller can install or run a plug-in |
| [Splash's math compiler](#splash-math-and-compute-kernels) (makepad) | Generated by makepad from Splash code | makepad-stitch, an interpreter | Linked into every build | Not used: OctoSense links nothing that calls it |

## An app's own functions: the `wasm` service

[ADR 0011](adr/0011-apps-own-functions-in-webassembly.md) (Accepted, with
limited support) lets an app ship Rust functions compiled to WebAssembly in
its bundle, and the shell runs them for that app only. They are for light
computing beside a script: parsing, ranking, scheduling, diffing, a format
conversion. Splash's compute kernels stay the answer for numeric work.

### The module

A module is core WebAssembly at `fns/<name>.wasm`, at most 8 per bundle. There
is no component model and no WASI.

- It exports `memory`, `octo_alloc(len) -> ptr` and `octo_free(ptr, len)`.
- Every other export of type `(i32, i32) -> i64` is a function: it takes its
  input at `(ptr, len)` and returns `(out_ptr << 32) | out_len`. The output
  starts with a status byte, `0` for success and `1` for an error, whose text
  follows.
- Its only import may be `octo.log(ptr, len)`. A module that imports anything
  else is refused when it loads.
- It has one memory and at most one table.

The guest crate
[`apps/wasmlab/guest/octosense-guest`](../apps/wasmlab/guest/octosense-guest/src/lib.rs)
writes all of this: `export!` for `fn(&[u8]) -> Result<Vec<u8>, String>`,
`export_json!` for serde types, and `log`. Build the crate as a `cdylib` for
`wasm32-unknown-unknown`. Builds for `wasm32-wasip1`, wasm-bindgen output and
components import functions the shell does not provide, so they do not load.
App developers start from App Flow's
[Run your own Rust code](https://github.com/OctoSense-org/OctoSense-App-Flow/blob/main/docs/RUST.md).

### How a module reaches a device

- **A store app.** App Hub's gate (app contract 1.7.0) admits a `.wasm` file
  only at `fns/<name>.wasm` (the name `[a-z0-9_-]`, at most 64 characters), only
  as a core module (it checks the file's first eight bytes), at most 8, and
  only with the `wasm` capability. A `wasm` capability without modules is a
  warning. The gate does not read a module's imports or exports: the shell
  checks those when the module loads. The store tells the person: "Run its
  own sandboxed functions on this device." The rules are in App Hub's
  [publishing reference](https://github.com/OctoSense-org/OctoSense-App-Hub/blob/main/docs/PUBLISHING.md)
  (the `functions` finding and the `wasm` capability).
- **A system app.** It is packed into the shell like any other, by digest,
  from the packaging's system-app list. `desktop/system-apps-wasm-lab.json`
  and `phone/system-apps-wasm-lab.json` are the standard lists plus `wasmlab`.

### The service

The `wasm` host service (`crates/shell/src/wasm_service.rs`) is in every
standard desktop and Home build on macOS, Linux and Android: the shell's
`wasm-functions` feature, on by default in both packages (`wasm-lab` is its
former name). Builds for Windows, iOS and OpenHarmony leave the runtime out
(`crates/shell/Cargo.toml`, `crates/shell/build.rs`), and there a call answers
`no service answers "wasm" on this device`. It answers two kinds of request:

- `wasm.functions`: the functions the app's modules export, how each module
  loaded (compiled, or from the cache, and how long it took) and how each
  function has run.
- `wasm.<function>`: one call. A string argument goes in as its text, anything
  else as JSON. JSON output comes back as data, anything else as
  `{"text": …}`. The function's own error, a trap or the deadline is the
  request's error.

The code always comes from the calling app's own admitted, digest-checked
bundle, never from an argument, and no app reaches another app's functions.
The Card runner's gate and the tool executor require the `wasm` capability,
and the service checks the admitted manifest's grant again before it loads
anything.

Every call gets a fresh instance: memory, globals, tables and log lines from
one call never reach the next, including after a success or the function's
own error. Only compiled code is reused, in the app's worker and in a disk
cache (`wasm-cache` in the host directory, keyed by the module's SHA-256 and
the engine's compatibility hash). The service checks admission again before a
call runs and before its answer is delivered. An update, a changed grant or a
signed withdrawal discards the answer and the compiled code. Compiling cannot
be interrupted, but an expired or cancelled request never goes on to run.

| Limit | Value |
| --- | --- |
| One call, start function included | 2 s of wall-clock time (checked every 10 ms) |
| Linear memory | 256 MiB |
| Table elements | 16,384 |
| Wasm stack | 512 KiB |
| Module | 8 MiB |
| Input or output of one call | 16 MiB in the runtime; 1 MiB of serialized input in the service |
| Log | 64 lines a call, 1 KiB each |
| Modules per app | 8 |
| Apps running functions at once | 4 workers, one per app |
| Queued requests | 4 per app |
| Buffered input, all apps | 16 MiB |
| One request, queueing and loading included | 10 s |
| An idle worker | exits after 5 s |

A full queue or no free worker fails the request at once instead of making it wait.

### Agent tools

An app's `tools.json` may map a tool to one of its functions with
`"host_method": "wasm.<function>"`. That needs the `wasm` capability. Unlike
shared host methods it has no minimum risk and needs no
`"private_data": true`, because the function sees only the arguments it is
given. Wasm Lab maps `wasmlab.find_slots`, `wasmlab.rank` and `wasmlab.diff`
to `wasm.find_slots`, `wasm.fuzzy_rank` and `wasm.text_diff`, all `read`.

### Platforms

| Platform | State |
| --- | --- |
| macOS | Runs. Validated in a hidden desktop shell (ADR 0011). Wasmtime catches traps with Mach exception ports, not signals. |
| Linux | Runs. The runtime and service tests pass on x86_64, with traps caught by signals, and Wasm Lab ran in a headless desktop (8 October 2026). |
| Android | Runs in Home's default build. Needs libc 0.2.190 or later, which `crates/wasm-host` requires: with 0.2.189 every trap ended the process. Validated on a Redmi Note 12 (ADR 0011) and by the [phone acceptance](#phone-acceptance) on a OnePlus 6. The runtime adds about 7.5 MiB of code; compiling a 433 KiB module takes about 0.4 s on a Snapdragon 685, and loading it from the cache 5–11 ms. |
| Windows | Not included. The runtime stays out until it has been checked on Windows. |
| iOS | Not included. Apps may not JIT there; the option is Pulley, Wasmtime's interpreter, about 17 times slower than Cranelift. |
| OpenHarmony | Not included. Its JIT policy is **unverified**. |

On a managed Mac, Microsoft Defender holds the first open of a freshly written
cache file for about a second; ADR 0011 has the measurements.

### Wasm Lab

Wasm Lab (`os.wasmlab`, `apps/wasmlab/`) is the system app that shows the
service. It is a demo: standard builds do not ship it. Its functions
(`apps/wasmlab/guest/functions`) are Markdown to HTML (pulldown-cmark), free
slots around busy times, fuzzy ranking (strsim), a line diff (similar), and
`rogue`, which loops forever, allocates without end, panics or recurses
without end on request. Its screen calls each one through `host.request` and
shows what came back, the round trip and `wasm.functions`.

Build a desktop with it, then start it with Wasm Lab open, hidden and driven
over the remote control surface (`/help` lists the routes; end with `/quit`):

```sh
OCTOSENSE_SYSTEM_APPS=$PWD/desktop/system-apps-wasm-lab.json cargo build --locked -p octosense
MAKEPAD_HIDE_WINDOWS=1 target/debug/octosense --remote=47631 --test-action launch-wasmlab
```

On the Linux build host (8 October 2026; a default debug build, hidden, under
a headless Weston), the module compiled in 98 ms on first use and loaded from
the cache in 4 ms after that, also after a restart. Each misbehaving mode
ended in an error and the shell kept running: the endless loop at its deadline
after 2,039 ms, endless allocation at the memory cap after 340 ms, and the
panic and runaway recursion after 37 ms each, as the script timed them.

When it opens, Wasm Lab makes its four calls first and asks for
`wasm.functions` once they have answered: the service queues at most four
requests per app. `wasm.functions` counts calls since the app's worker
started; a worker exits after five idle seconds, and the counts start again
with the next one.

The checked-in module rebuilds byte for byte: with rustc 1.97.1,
`apps/wasmlab/guest/build.sh` writes the same `bundle/fns/wasmlab.wasm`
(SHA-256 `f4a69c32…`). It needs the target once:
`rustup target add wasm32-unknown-unknown`.

### Tests

```sh
cargo test --locked -p octosense-wasm-host
cd phone && cargo test --locked --features mobile-apps -p octosense-shell wasm_service::tests
```

- `crates/wasm-host/tests/runtime.rs` runs a hand-written guest: input and
  output, guest errors, the deadline, the memory, table and stack caps, traps,
  the import rule, per-instance state, threads, the size limit, the cache and
  its concurrent writers, cancellation.
- `crates/wasm-host/tests/guest.rs` runs Wasm Lab's module and compares every
  function with the same Rust run natively, then every `rogue` mode.
- The service tests cover the tool mapping, bounded input, a fresh instance
  per call, revocation after an update, a grant change or a withdrawal,
  cancellation and the queue bounds, and the app's own functions answering
  its tools and its script.

`phone.yml` runs the first command, and the service's tests as part of Home's
(`mobile-apps` includes `wasm-functions`); `tools/ci-local.sh --linux-host
--offload` runs both on the Linux build host. Every CI build of the desktop
and Home includes the service, and `tools/check-shell-graph.sh` checks that
its runtime is linked exactly on macOS, Linux and Android.

### Phone acceptance

[`tools/fixtures/wasm-phone-lab`](../tools/fixtures/wasm-phone-lab/README.md)
holds a synthetic signed store app, `org.octosense.samples.wasmprobe`, whose
module (`state.wasm`, from `state.wat`) remembers its last input if its
instance is ever reused. `crates/wasm-phone-smoke` packages it in a test APK
that installs it through the normal signed store and calls it through a real
script tool, and `tools/test-wasm-phone.py` drives that on an assigned
device. Its [receipt](../tools/fixtures/wasm-phone-lab/acceptance-oneplus6.json)
records 22 of 22 checks passed on a OnePlus 6 with Android 15, including a
fresh instance after a success, a guest error, a trap and the deadline. Its
source, e67ce63e, has the wasm service and runtime that `main` has. A live
model, performance and a release APK were not part of it. `state.wasm`
rebuilds byte for byte with the fixture README's `encode_phone_fixture`
command.

### Not done yet

- No release includes the service yet: the first desktop and Home releases
  built from `main` after #400 will.
- Windows, iOS (Pulley) and OpenHarmony.
- CPU fairness between apps, and a bound on the disk cache, which nothing
  evicts.
- Compiling at install time (store apps) or build time (system apps), to
  remove the first compile on a phone.
- Typed interfaces (the component model and WIT) instead of JSON. Any import
  beyond `octo.log`, such as a clock or randomness, would be a new
  capability.

## Engine plug-ins: the `photo` and `vector` services

Two engines of ADR 0013 host their own WebAssembly plug-ins, in wasmi, a
pure-Rust interpreter, each in a registry that belongs to the process, not to
a call:

- photocraft, the raster engine behind the `photo` service
  (`apps/photo/host-service`): filter plug-ins with no imports, 32 MiB per
  module, 512 MiB of memory per instance, 50 million instructions per call
  and 60 s per run.
- vectorcraft, the vector engine behind the `vector` service
  (`apps/vector/host-service`): object filters and live effects with no
  imports, a fuel budget, a memory cap and a fresh instance per run.

effectcraft, behind `effect`, has WebAssembly plug-ins too, behind an optional
feature; OctoSense does not link its plug-in crate. vectorcraft's desktop UI
crate has a second install command, `ui.installPlugin`; OctoSense does not
link that crate either.

**Closed since #398.** `photo.run` refuses every `plugin.*` command before the
engine sees it, and `photo.commands` leaves them out. Before #398 a caller
could install a plug-in from base64 `data`; it went into photocraft's
process-wide registry, outlived the call and served every later caller, under
limits far above the `wasm` service's. A scratch program that calls the
service as a script's `host.request` does showed both, on the Linux build host
(8 October 2026). Before #398, `os.photos` installed photocraft's example
plug-in, the next call listed it, and another system app, `os.notes`, ran it
on a document. With #398, each of those calls is refused:
``photo.run: `plugin.install` is not available through the photo service``.

**Closed in `vector` by #405.** `vector.run` refused files, documents, the
`app.*` group and path-like arguments, but not `plugin.*`, and vectorcraft's
engine installs a plug-in from base64 `dataBase64`. The same scratch program
showed it on `main` before #405: `os.notes` installed vectorcraft's example
plug-in, the next call listed it, another system app (`os.maps`) saw it, and
`vector.commands` offered `plugin.install`. Now `vector.run` refuses every
`plugin.*` id before the engine sees it
(``vector.run: `plugin.install` is not available through the vector service``),
and `vector.commands` leaves them out.

Both engines still link wasmi, and both services answer system apps (`os.*`)
only.

**The UI thread.** The `photo` service, like the other engine services, does
its work inside the request. App Hub dispatches a script's `host.request` on
the UI thread, and calls the service while it holds the lock on the service
registry (`services::dispatch`). So a long `photo.run` holds up the UI and
every other app's requests until it returns
([#399](https://github.com/OctoSense-org/OctoSense/issues/399)).

## Splash math and compute kernels

makepad's script engine can compile a pure-math Splash function, such as a
signed distance field, into a WebAssembly module it generates itself, and run
it in makepad-stitch, its own interpreter, as the reference that matches the
Splash interpreter bit for bit
(`.sources/makepad/platform/script/src/math_aot/`). No app supplies that
module. In OctoSense only makepad's CSG library would call it, and OctoSense
does not link that library, so the code is present and unused. ADR 0011
measured stitch for apps' functions (2,942 CoreMark against Wasmtime's
44,534) and did not choose it.

makepad's compute kernels also have a WebAssembly backend, but it runs only
when makepad itself is compiled for `wasm32` (a browser). Native builds use
their native backends.

## The shell in a browser

The shell keeps the `wasm32` paths of makepad's window manager, its "web
superbuild": no child processes (`crates/shell/src/host.rs`), every native app
hosted in process (`tools/native_apps.py` gives each app a `wasm` hosting of
`module` or `none` in `crates/shell/src/native_apps.rs`, and refuses
`process` there), and in-process service links for the assistant
(`crates/shell/src/pane_links.rs`). App Hub reports such a host's platform as
`web`.

No build, CI job or release produces it, and it does not compile. This check
on the browser target fails:

```sh
cargo check --locked --keep-going --target wasm32-unknown-unknown -p octosense-shell --no-default-features
```

getrandom 0.2 and 0.3, uuid, fs2, ring and aws-lc-sys fail to build for that
target. Even without default features the shell links `octosense-ai-host` and
App Hub's crates, which bring in most of them (credential encryption, sigstore
verification, TLS, file locking); the shell's own `uuid` lacks a randomness
source there. Treat these paths as unmaintained.
