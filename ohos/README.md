# OpenHarmony support files

`makepad-ohos.patch` is the diff the sibling `../guofoo-makepad` checkout needs on top of the pinned revision in `upstream/makepad.json` to compile and run on OpenHarmony (branch `makeos-ohos` there). It only touches code that OpenHarmony would otherwise inherit from desktop Linux (it reports `target_os = "linux"`), plus two device fixes:

- `platform/src/gl_render_bridge.rs`, `platform/src/cx_api.rs`: the desktop GL bridge and video probe use state OpenHarmony's `CxOs` does not have.
- `platform/build.rs`: no xkbcommon in the OpenHarmony sysroot.
- `platform/network/src/{backend.rs,blocking_http.rs,socket_stream.rs}`: the Linux network backend links OpenSSL, which the sysroot lacks (it ships `libnet_ssl`/`libohcrypto`). HTTPS is reported unsupported on OpenHarmony until a backend exists.
- `platform/src/app_main.rs`: the OpenHarmony entry never installed the logger, so `log!` went to stdout instead of hilog.
- `platform/src/os/linux/open_harmony/*`, `platform/src/cx_api.rs`: dependencies (fonts, icons) are read lazily from the HAP's rawfile store; the startup table is filled before any crate registers, so no text rendered.
- `tools/cargo_makepad`: the dependency-resource scan now honours `--config`, so crates reached through a `[patch]` still get their `resources/` staged.
- `platform/src/remote.rs`, `platform/src/os/linux/open_harmony/open_harmony.rs`: makepad's `--remote` observability surface runs on OpenHarmony. `aa start ... --ps makepad.NAME VALUE` launch parameters become environment variables (the ArkTS glue forwards `makepad.*`), so `MAKEPAD_REMOTE=0.0.0.0:PORT` binds the HTTP control surface on the phone; the event loop services it and answers `/g` grabs from the presented framebuffer. The display context is populated before Startup, as on Android.
- `widgets/src/desktop_style.rs`: OpenHarmony phones take the `android` widget style by default, as Android does.
- `draw/src/shader/draw_text.rs`: the text renderer's Linux/Windows arm defers a glyph that still needs uploading to a desktop-side flush the OpenHarmony loop never runs, so text first needed later (inside a module) stayed invisible; OpenHarmony now takes the arm Android takes.
- `platform/src/script/res.rs`: a crate-relative resource path that escapes its crate (`self:../../widgets/resources/font.ttf`) gets its package key from the crate manifests on every target, not only on the web, so a packaged build finds it; load outcomes are logged on OpenHarmony.
- `platform/src/os/linux/open_harmony/open_harmony.rs`: the startup dependency loader (the app's `font_assets`) uses the HAP's `makepad/<crate>/...` layout, so a font listed there no longer records a permanent failure.
- `platform/src/script/res.rs`: when several script "crates" share one manifest directory (a theme sheet registers as `desktop_style_omarchy_theme` from the widgets directory), the package key prefers the crate named like its directory; the Sheets mono font was mapped to the theme pseudo-crate and never loaded on the phone.
- `apps/sheets/src/view.rs`, `widgets/src/data_grid.rs`: the spreadsheet's phone version. When the active style is a phone (iOS, Android, OpenHarmony via the android style) the family registers with finger-sized chrome, taller rows, larger cells and fonts, no path field, and `touch_pans` on the grid, where a finger pans and a tap selects while the mouse keeps drag selection. The same source renders the desktop layout under a desktop style, and the desktop's Android emulation shows the phone layout.

- `apps/*` (clock, weather, task, mixer, terminal, files, image, pdf, video, score, fabric, route, fab): each app is split into a library crate with an in-process `AppModule` (a `*View` root widget the window manager seats in an isolate) and a thin standalone `main.rs` behind a `standalone` feature. A phone cannot spawn child processes, so this is how every catalog app runs there; the same modules also host in the desktop's Android emulation. Sheets and Photos were already modules. The binary target names are unchanged, so the desktop catalog still launches each app as a process.

- `platform/src/os/apple/apple_util.rs`: a macOS crash fix (unrelated to OpenHarmony but carried on the same branch). `load_undocumented_cursor` passed the BOOL from `respondsToSelector:` back into `performSelector:` as the selector, so dragging a window corner (which uses the undocumented diagonal resize cursors) performed a garbage selector and segfaulted. It now performs the selector only when the class implements it, falling back to the arrow cursor.

- `platform/src/remote.rs`, `platform/src/os/linux/open_harmony/open_harmony.rs`: the `--remote` harness gained `/perf`, and the OpenHarmony loop feeds the platform's `PerfMonitor` (draw, swap wait, vsync wait, messages, shader compile, platform ops, touch-to-paint), which only the Metal backend fed before.
- `platform/src/os/linux/open_harmony/{oh_sys,oh_callbacks}.rs`: the vsync connection declares a 60–120 Hz expected frame-rate range and enables DVSync (API 20+/14+).
- `libs/wm_theme/src/lib.rs`: `current()` is memoised by the theme file's path and mtime. On the phone every app's colour lookup called it per frame, and each call opened and read the theme file; file I/O was the top of a drag profile.
- `apps/sheets/src/theme.rs`: the colour builder's fallback no longer re-reads the theme for every key.

- `platform/src/os/linux/vulkan.rs`, `platform/src/os/linux/open_harmony/vk_native.rs`, `platform/Cargo.toml`, `platform/src/os/linux/mod.rs`: the Vulkan backend on OpenHarmony (`MAKEPAD=vulkan`). A shim wears the NDK names the backend was written against (`ANativeWindow` refcounted through `OH_NativeWindow_NativeObject{Reference,Unreference}`, hardware buffers as inert stubs), the surface comes from `VK_OHOS_surface` (`vkCreateSurfaceOHOS` fetched by proc address), the loader is `libvulkan.so` (not the desktop `.so.1`), the device asks only for the swapchain extension and enables the YCbCr sampler feature only where offered, and the loader's INFO chatter is not logged. `platform/script/src/shader_wgsl.rs` now emits the `_mp_unpack2f16` / `_mp_unpack4u8` helpers the backend maps to, which no WGSL shader defined.
- `platform/src/os/linux/vulkan.rs` (all Vulkan targets, Android included): off-screen passes record into a ring of command buffers and are submitted without a CPU wait, with frame-lifetime resources freed one frame later; each pass used to block on its fence, which cost 28 ms of a 33 ms frame on the phone. Pipelines are built against a `VkPipelineCache` seeded from disk and saved back (`set_pipeline_cache_path`). The present path's sync points and pipeline builds are timed into the PerfMonitor. Untested on Android in this work.

- `platform/src/remote.rs`: `POST /put?path=<relative>` writes the raw request body under the makepad home. A phone's app sandbox cannot be written by the hdc shell (SELinux), so test data such as a baked map goes in over the harness port: `curl --data-binary @amsterdam-base.mbtiles http://<phone>:8399/put?path=maps/amsterdam-base.mbtiles`.
- `platform/src/os/linux/open_harmony/open_harmony.rs`: `StartLocationUpdates` answers with `LocationError::Unavailable` (Route shows "gps: unavailable" instead of "Locating…" forever); a real LocationKit backend needs the `ohos.permission.APPROXIMATELY_LOCATION` grant from the ArkTS side first.
- `apps/route/src/provisioner/native.rs`: a finished test-map bake found under the maps root at startup is adopted as the map (it needed an in-app bake before), so a map baked with `makepad-map-tiles testmap` and copied to the device draws without any network. `draw/src/vector/triangulate.rs`: the road z-bias tick clamps to the f16-exact range instead of failing the tile's bake on a debug assertion (Amsterdam's centre reaches 2049).
- `platform/src/os/linux/vulkan.rs` (`painters_order`): the map (makepad's map widget, used by Route) draws its tiles into an off-screen texture that has a depth attachment; the Maleoon driver on this phone silently drops that depth buffer's clear, so it reads back as 0.0 and every tile fails the `LESS_OR_EQUAL` depth test — only the window-pass labels showed. On OpenHarmony the backend builds pipelines with depth compare `ALWAYS` (painter's order, depth still written); the tiles are already submitted back-to-front with a per-draw z-bias, so this matches the desktop result including the tilted 3D view. Confirmed with a reversed compare op and with the depth test off, both of which render the full correct map. A launch parameter `makepad.MAKEPAD_LOG_VERTEX_LAYOUT 1` logs the typed vertex-fetch layout and per-pass draw stats for future debugging; it is inert otherwise.
- `platform/src/os/linux/vulkan.rs`: the per-frame packet buffer, when it grew mid-frame, was destroyed while every draw already recorded still referenced it (uniform descriptors and instance binding) — early draws of a heavy frame were dropped and the device was occasionally lost; it is now retired with the frame, as are replaced geometry buffers. Typed (compact) vertex records are fetched as raw `u32` word chunks and unpacked in WGSL (`platform/script/src/shader_wgsl.rs`), with u16 index buffers; the map's tiles still do not appear on the phone (see the memory notes for the open investigation and the `MAKEPAD_VK_DEBUG_TYPED*` / `MAKEPAD_LOG_VERTEX_LAYOUT` launch parameters that probe it).

Apply with `git -C ../guofoo-makepad apply ../makeos/ohos/makepad-ohos.patch` on a checkout at the pinned revision. `scripts/ohos.sh` builds against that checkout.
