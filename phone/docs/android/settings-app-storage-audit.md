# Per-app storage and cache: next-slice audit

This began as a read-only design audit against pinned Settings `0f0669fc699f70adb20fe6ed4b2ff1c600da6f86`. The bounded storage implementation passed native emulator acceptance on Home2026092528:129 checks on disposable emulator-5560. Current OctoSense App details already observes StorageStatsManager app/data/cache bytes, distinguishes unavailable access, and discloses shared UIDs.

The native reference is `applications/AppStorageSettings.java`, with framework ActivityManagerService clear-data and PackageManagerService cache operations. Native Clear cache invokes `PackageManager.deleteApplicationCacheFiles` asynchronously. Clear storage either launches the package's own `manageSpaceActivityName` or shows the platform clear-data confirmation before `ActivityManager.clearApplicationUserData`. Storage reads are async; action completion is separate from a successful enqueue. A package can recreate cache immediately, so a successful callback does not imply a permanent zero-byte observation.

The framework cache API specifically enforces `INTERNAL_DELETE_CACHE_FILES`; a caller holding only the old `DELETE_CACHE_FILES` permission is silently ignored and receives no completion. PackageManager queues the operation and resolves the package again under its install lock. Its callback is not a byte-count proof, and the public operation does not accept an expected APK incarnation. The adapter must check incarnation immediately before enqueue and again on completion, reject old reviews, and disclose an uncertain result if identity changes; it must not claim atomic protection across a package replacement racing the framework queue.

## Proposed bounded increment

Use Apps → App details → Storage & cache with the existing trusted Settings root and a dedicated finite system-UID Broker API. Observe exact package incarnation, volume/storage identity, current bytes, policies and offered actions. The available commands should be read, review clear-cache, review and request clear-data, and validated package-owned manage-space navigation. Do not expose paths, raw package-manager calls, arbitrary intents or arbitrary file deletion.

Clear cache should require explicit review in OctoSense, one-use observed authority and an async native completion operation ID. Clearing app data is destructive and is confirmed in the trusted built-in Octoscript Settings page, showing the exact app and the effects on saved data, permissions and background work. The review is bound to an expiring one-use package/volume/authority observation. Byte counts are re-read for current eligibility but are not included in the target identity: ordinary cache growth must not invalidate an otherwise unchanged review. The Broker re-resolves the package incarnation, current stats availability, supported action and policy before enqueue, including after package reinstall while a review is open. Neither rotation nor returning to the page replays a request. Native package-owned Manage space remains provider-owned; verify the exact declared Activity belongs to the current package, is enabled/exported as required, and use a fresh task so Cancel/Back returns correctly.

Follow native policy gates: `DISALLOW_APPS_CONTROL` (base or administrator), Mainline modules, current-user visibility, active administrators, and system packages without `FLAG_ALLOW_CLEAR_USER_DATA`. Retain framework enforcement as the final boundary. Shared-UID data requires particular care: deny mutation in this first increment unless the platform operation's exact package/UID effects are proven and the user is shown the affected identities. Protect the running OctoSense Home, Agent, Broker and Quickstep, plus the native launcher/Settings infrastructure so the settings operation cannot destroy its own confirmation/control state.

Native app-data clearing also stops the package and resets permission/notification/URI state through the framework. The UI must describe those effects and report completion only from the native callback plus fresh observations. Do not reproduce the operation using filesystem deletion or bypass the ordinary framework permission-reset path.

ActivityManagerService additionally cancels jobs (including proxied jobs) and alarms for the UID. That makes shared-UID denial especially important. The ordinary clear-data route uses `restorePregrantedPermissions=true`; `clearApplicationUserDataWithoutPermissionReset` and `keepState` exceptions are not appropriate user-facing substitutes.

## Acceptance proposal

Use only disposable fixture APKs on the owned privileged clone. Seed distinct internal data, cache, code-cache and external app-specific test files, with a fixture-owned public report of existence/length. Verify cache-only clear preserves durable data; clear-data Cancel/Back/rotation preserves all files and grants; positive confirmation resets only the target's data; old confirmation after reinstall is rejected. Exercise a package-owned Manage space Activity and return behavior. Verify locked/user/policy/protected/shared-UID denial and asynchronous failure/timeout without duplicate deletion. Capture all other package grant/AppOps/policy records and package identities before and after, and remove fixture packages at cleanup.

Ordinary emulator validation should prove unavailable controls, real statistics where access is granted, and explicit native recovery. The whole operation must stay off physical phones and real user data. Moving apps across volumes, all-app cache cleanup, document URI revocation, removable/adoptable-media formatting and storage category accounting remain separate parity items.

Ordinary Home 2026092526 acceptance on emulator-5556 passed unavailable controls/recovery (24 checks), eight cold launches (33 checks), and accessibility/IME smoke (33 checks), with no crashes. The synthetic storage fixture uses shell-gated ordered receivers for seed/read observations; ten repeated producer/reader checks preserved its URI grant. Nested instrumentation had force-stopped the measured package and invalidated the grant, so it is not used for these observations. These checks do not establish privileged clear-cache/data behavior; that acceptance is separate.

Native acceptance exposed an overly strict review revision: cache growth during confirmation rejected an otherwise unchanged app. Review now binds package incarnation, volume, UID membership, policy, declared manage-space Activity, valid stats and action eligibility; exact byte counts remain observations. The user authorizes the current app data/cache, whose size can change while an app runs. Fresh stats must still make the selected action eligible; package replacement, a lost capability or unreadable stats still deny the request.
