# App Hub implementation plan

**Goal:** Add a native App Hub module to OctoSense-mobile with browse, search, details, verified installation and launch. Follow the supplied App Store references with OctoSense styling. The signed live catalog and explicitly selected preview catalog remain separate.

**Architecture:** `apps/app-hub` owns native views and presentation state. The pinned OctoSense-App-Hub repository supplies catalog verification, bundle installation, policy and the existing contained Card module. The shell owns launcher identity and installed app discovery. Network and filesystem operations run off the UI thread.

**Design workflow:** Apply `Octoscript-AppCard/lab/image-to-appcard*`: preserve reference provenance, define scene semantics and native control mappings, isolate raster artwork, and inspect actual native captures. The production shell is a native Makepad app, so its responsive views implement the scene contracts directly; no screenshot backgrounds or invisible hotspot UI.

## Tasks

1. Catalog service and model (`apps/app-hub/src/catalog.rs`, crate manifest): add meaningful tests for live/preview separation, search, cached verification and installation policy; implement asynchronous service over the pinned Hub backend. Preview apps are existing built-ins and can open them, never install fake bundles.
2. Native design and views (`apps/app-hub/src/view.rs`, `module.rs`, resources and `docs/design/app-hub`): Today, Apps, Search, Library, detail/permissions, empty/loading/error states. Use native text, controls and scrolling; permission confirmation precedes verified installation. Preserve draft query and stable app selection across refreshes.
3. Shell integration (`Cargo.toml`, `src/apps.rs`, `src/main.rs`, launcher/style/config): register App Hub and contained Card host, discover installed apps, route launch actions with unique installed app identity, share persistent installation root.
4. Verification: run focused model/service tests, shell regression tests, release Android build, install and inspect connected device. Exercise preview browse/search/detail/open and live empty/error states. Exercise signed fixture install/open where feasible because production catalog is empty. Review spec then code quality and resolve findings.

## Acceptance

- App Hub appears alongside News and Maps and works on mobile.
- Live data comes only from the verified Hub catalog; cached catalog rollback and stale-install restrictions stay enforced.
- Preview is explicitly labeled and separately selected, with no fabricated production listings.
- All visible primary controls perform their described actions; installed apps open in the contained Card module with distinct identities.
- Native screenshots show readable titles, artwork, list rows and safe bottom navigation at actual device size.
- Test/build evidence and remaining limitations are recorded without claiming unrun checks.

## Delivery notes

The feature lives on `feat/app-hub`. Native visual evidence and source
provenance are in `docs/design/app-hub/`; run and fixture instructions are in
`apps/app-hub/README.md`. The signed local catalog is generated only in the
ignored `target/` directory and never becomes a production listing.

Validation covers the actual shell in its 412×892 phone layout, including
verified installation, two distinct installed apps, launcher/Recents identity,
and opening the existing Photos app from preview. The Android artifact is
`target/android/makepad-android-apk/octosense/apk/octo_sense.apk`.
The later icon follow-up was installed and inspected on a Pixel 7 Pro; its
captures and checks are recorded in `docs/design/app-hub/store-logo-validation.json`.

The runtime dependency change is an explicit consumer override to Makepad
`7786bb4a3`, adding the containment APIs required by the Hub runner. The shared
Octoscript-Makepad release remains pinned at `b0628d05`; the setup tool verifies
this combination and refuses dirty or inconsistent checkouts.
